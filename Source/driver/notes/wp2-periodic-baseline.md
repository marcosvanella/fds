# WP2: periodic 128^3 CPU baseline (stage-1 GPU spike plan, `docs/amrex/stage1-gpu-spike-plan.md`)

## What is committed
- `tests/make_periodic_case.py <N> <outdir> [t_end] [sx sy sz]`: generates the fully periodic Taylor-Green LES case (`tg<N>.fds`, `tg<N>_uvw.csv`; the csv is 56 MB at N=128 and is **not** committed, it is regenerated).
- `tests/run_big_periodic_baseline.sh <driver-build> <off-build-dir-with-fds> <work> [N=128] [steps=10]`: generates the input, runs the driver (`fds_amr --run`, 1 rank, `FDSTL_PROFILE=1`) and the `USE_AMREX=OFF` FDS on the same input with the same T_END (10 steps of dt = 9.38e-3 s), and writes `<work>/baseline.csv` (wall, peak RSS of the largest rank, loop time, pressure time, `f_pres`). A memory watchdog kills a run if less than 350 MB is available.
  Example: `tests/run_big_periodic_baseline.sh <build>/on <build>/off /workspace/fds-amr/scratch/role1-s8-work/wp2 128 10`.
- Input actually used for the numbers below: `/workspace/fds-amr/scratch/role1-s8-work/wp2/tg128/` (case) and `.../wp2/run_driver`, `.../wp2/run_off` (outputs).
- Case: one 128^3 mesh, box 0.56549 m, six `PERIODIC` vents, constant Smagorinsky, ideal gas single species, no slices, `FFT` pressure (driver: `pressure_backend` FFT backend; OFF FDS: its own Poisson solver), 10 steps, 1 rank, threads = 1.

## Numbers (box with 1 core; measured while other jobs were running: load average 3.5 for the driver run and 6.2 for the OFF run, so they are NOT valid as idle-machine numbers (NFR-030) and the driver/OFF ratio is not to be quoted)

| variant | wall s | loop s | pressure s | `f_pres` | peak RSS (one rank) |
|---|---|---|---|---|---|
| driver (this run, load 3.5) | 76.6 | 65.2 (`t_loop_s`) | 21.0 | 0.323 | 2.54 GB |
| OFF FDS (this run, load 6.2) | 105.9 | 97.4 (Total T_USED of `_cpu.csv`, includes 9.6 s DUMP, 5.8 s COMM) | 25.6 (`PRES`) | 0.263 (PRES / Total) | 2.02 GB |
| driver (earlier, S8, lighter load) | 70 | 57.6 (5.8 s per step, 2.7 us per cell and step) | 18.7 (FFT solve 6.7 s) | 0.324 | 2.54 GB |

For the GPU plan: the driver's per-step cost on this CPU is 5.8-6.5 s for 2.1e6 cells; the pressure share is about one third (`f_pres` 0.32, stable across the two driver runs although the absolute times moved by 13%); the output writers are 3.2 s of the loop in the driver (FDS's own writers, `FDSTL_NO_FDS_OUTPUTS=1` removes them). `fill_omesh` (the OMESH copy that `EXTERNAL_GHOSTS_FILLED` leaves in place for the NO_FLUX / MATCH_VELOCITY_FLUX readers) is 16 s of 57 s at 128^3 on one box, the largest avoidable host cost (S8 profile); on one box it copies the box onto itself.
The driver's RSS is 26% above FDS's (probably the AMReX scratch and solver arrays on top of the FDS allocations; not analysed).

## Not done / needs an idle machine
- Idle-machine repetitions (3 reps, load < 1, >= 6 GB free) of both variants: ask the project coordinator for a quiet slot; the script does the whole sequence and records the load before each run.
- 192^3 does not fit in the box memory (extrapolated 8.6 GB RSS for the driver).
- The 4-rank / multi-box variant of the same case (`make_periodic_case.py 128 <dir> <t_end> 2 2 1` + `mpirun -np 4`) is generated by the same script; not run here (one core).
