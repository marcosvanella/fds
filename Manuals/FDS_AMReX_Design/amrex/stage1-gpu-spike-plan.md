# Stage-1 GPU spike: plan and first piece

Scope: stage 1 of `docs/adr/drafts/gpu-staging-plan.md`: generated K2 cell kernels (branch `s5-gen`, HEAD `6c87023310`, `S5_CALLEE_DPD`) on real FDS fields, data resident on the GPU, device FFT pressure solve for a periodic case, end-to-end step time against the CPU driver, bitwise or tolerance check against the CPU driver. Related documents: `docs/amrex/flux-hooks-kernel-review.md` (review of the flux-hook kernels, section 7.11 below) and `notes/wall-seam-design.md` of the driver (wall-state seam). Labels: **run** = executed; **compiled** = built only; **read** = from source or documents; **ESTIMATE** = not measured, basis given. A figure is marked *partly synthetic* where some of its inputs are substitutes (stated at the figure). GPU: cc 8.9 test-machine GPU (8 GB), nvfortran 26.9, `-O2 -mp=gpu -gpu=cc89,nofma -Minline`, nvcc `--fmad=false`, AMReX CUDA build without fast math.

## 1. What exists today (survey of `Source/driver`, read-only; read)
- **Fields:** `Fields.cpp` keeps 25 FDS arrays as one `MultiFab` each on the level-0 `BoxArray` (box = FDS mesh; ghost widths per D-031). The unmodified FDS Fortran sees FAB memory through `fds_shim_bind`/`fds_alias.c` (array descriptor aimed at the FAB), i.e. through host pointers.
- **Kernels:** `fds_kernels.f90` wraps whole unmodified FDS routines (`fds_k_visc`, `fds_p_dens_pre/post` with the D-031 gather clip between, `fds_k_vflux`, `fds_k_div1/div2`, `fds_k_vpred/vcorr`); `TimeLoop.cpp` calls them per box in MAIN_LOOP order. No generated, K1 or K2 kernel is called anywhere. The wall chain (`WALL_BC`, `MATCH_VELOCITY`, `VELOCITY_BC`, `VISCOSITY_BC`) is unmodified host code on `OMESH` copies filled from the FABs (`fds_g_fill_om`).
- **Periodic case:** periodic ghosts by `FillBoundary`; the two copies of a periodic face are averaged by `BcStep::match_periodic_faces`. FDS still holds periodic faces as `INTERPOLATED` wall cells, so the host wall routines still run: no case is truly wall-free in the FDS data model.
- **Pressure:** `solve_poisson` -> `pb::solve_pressure` (Role 2, `Source/pressure_backend`) -> `FFT::Poisson<MultiFab>`. The RHS goes Fortran -> host buffer -> MultiFab by host loops. Against FDS it is T2 only (H differs at about 1e-14).
- **Device readiness:** `ParallelFor` count is 0 in `Source/driver/*.cpp`, `pressure_backend/*.cpp` and `ExactSum.H`: every `Array4` loop (RHS fill, mean removal, residual, exact sums, ghost fills) is a host loop and would fault on device FABs.
- **AMReX options:** the existing test machine CUDA install has CUDA on, **FFT off, MPI off, OpenMP off**. The FFT component has cuFFT branches but needs `AMReX_FFT=ON` (new install). Runtime knobs: `amrex.the_arena_is_managed` (all FABs unified; ADR-001 rejects it for production, fine for a spike), `amrex.use_gpu_aware_mpi`; MLMG also runs on GPU.
- **CPU baseline (Role 1 S7 report, 1 rank, 1 thread):** `shunn3_32` 1.86 s for 80 steps, f_pres 0.59; `csmag_32` 0.60 s. A 128^3 periodic case now exists (`scratch/role1-s8-work/big/tg128`, Taylor-Green start): 10 CPU steps in 57.6 s (5.8 s per step, 1 rank, 1 thread, shared machine), `f_pres` 0.32 (FFT solve 6.7 s of the 18.7 s pressure scheme), 2.5 GB resident; of the 57.6 s, 16.4 s is `fill_omesh` (copy of every field into the FDS `OMESH` arrays, host only, not needed by a single box). 192^3 does not fit on the reference machine (about 8 GB).
- **Generated kernels:** 34, about 1.2% of modelled time. A periodic step needs 39 further loops, about 7.15% of modelled time (generator answers, `docs/amrex/stage1-generator-answers.md`): the `VELOCITY_FLUX` edge nests (3 loops, 0.68%, need edge tables) and 2 more, the `MASS_FINITE_DIFFERENCES` flux nest (4.83%, the largest) with `GET_SCALAR_FACE_VALUE` (0.28%), `VELOCITY_PREDICTOR/CORRECTOR` (front end accepts, untested; the MMS loops are dead code and stay on the host), `DIVERGENCE_PART_2`, `BAROCLINIC_CORRECTION`. `CHECK_STABILITY` (3 loops) and `CHECK_DIVERGENCE` are already translated and bitwise-tested by the generator (argmax with the serial `>=` tie rule).

## 2. Gap to GPU-resident stepping
(1) FABs sit on the host for the Fortran shim, kernels need device pointers: ruling (a) below, device arena with explicit staging at every host routine. (2) The driver calls whole FDS routines; a generated kernel replaces one loop inside one, so it needs a hook patch in the routine or driver stage code with host remainders (more hand-offs). (3) 34 kernels are not a step (section 1). (4) Driver and backend C++ are host-only. (5) The old test machine AMReX install had no FFT or MPI (now replaced by a separate FFT and MPI install, section 6.3); the `__int128` exact sums are unchecked on the device.

## 3. Decisions
- **(a) Memory (Architect, stands):** field data on the device arena in the CUDA driver build; managed memory only as a debug option. K2 uses `is_device_ptr`; explicit once-per-step uploads with checksums. Role 1 agrees: device arena with explicit staging around every host routine; managed memory only to count hand-offs.
- **(b) Kernel bounds, ruling withdrawn (owner decision D-052):** the `ILO..KHI` lower-bound arguments are deferred until a loop needs them; nobody starts them. Consequence (generator answers): a mesh split into several boxes works only if the driver hands each box to the kernel as its own array with local origin 1 (FDS ghost widths, box-local wall tables, sliced 1-D metric arrays, box-local coordinates for position-dependent callees); a box whose lower corner is not 1 cannot be run in place. Single-box runs are unchanged; the stage-1 spike stays single-box per mesh. Test-code exception: a minimal per-box wrapper that hands each box to the kernel as its own local-origin-1 array may be written in test code only (not in the driver), for the 1-box and 4-box device tests. Cost if it is ever needed: about 4 to 5 work-days (generator change, regenerate goldens, sub-box tests); WP0 and WP1 outputs are the regression set.
- **(c) Reductions, changed (owner decision D-053):** `CHECK_STABILITY` min/max unchanged (order independent; the recorded index follows the serial `>=` rule, boxes merged by value and global linear index). Zone sums (`DSUM/PSUM/USUM`) keep the FDS summation order by default: the device computes the per-cell and per-wall terms (elementwise, bitwise equal to FDS) and the additions are serial in FDS order (host or single-thread device pass), bitwise equal to FDS for one process. An exact fixed-point sum (order independent, not bitwise equal to FDS) is a switchable GPU option, off by default, tested separately; it needs `__int128` on the device checked (fallback two 64-bit limbs with carry) and is compared with a host reference summed in the same fixed point. The fixed-order per-box tree is dropped.
- **(d) Acceptance (Architect, stands):** as in section 5, measured against the CPU run of the same driver and layout; mass drift per step at most max(1e-13 relative, 2x the CPU drift). GPU flags rule NFR-051 applies (K2 `nofma`, nvcc `--fmad=false`, fast math off; host driver and FDS objects `-ffp-contract=off`).
- **D-050 (later, not now):** single global dt and interface flux overwrite (two-phase flux / override / divergence split; note `Source/regrid_transport/notes/flux-override-interface.md`); to be reviewed against this plan after stage 1.

## 5. Acceptance criteria
- **A1 kernels, bitwise:** each generated cell kernel, device vs the same file built for the host (gfortran `-O2 -ffp-contract=off`), on real frozen fields: 0 differing elements per output array (+0/-0 counts). Against the FDS result where the dump holds it: bitwise for pure loops; about 1e-15 relative where the FDS value includes a source term (stated per kernel).
- **A2 stage chain, bitwise:** pressure frozen (`FDSTL_PDUMP` fed to both), every `FDSTL_STAGE` array of a step equal between GPU and CPU driver.
- **A3 full periodic step, tolerance** (FFT sums depend on layout), against the CPU run of the same driver and layout: fields within 1e-12 relative, T/DT rows equal to the printed digits, MMS errors within 1.05x of the CPU driver (`shunn3_32`); zone sums bitwise equal to the CPU driver by default (D-053), the exact-sum option tested separately, mass drift per step at most max(1e-13 relative, 2x the CPU drift).
- **A4:** GPU run repeats bitwise.

## 6. Measurements (when WP4-7 exist; run)

### 7.1 WP0: ten generated K2 kernels on real fields, kernel level
Inputs: reference-dump records of unmodified FDS (`shunn3_32`, 32x1x32, 2 species; `csmag_32`, 32^3, 1 species), second step. The other kernels of the 34 need property tables or work arrays that the dumps do not hold.
- **Bitwise (run):** device vs host, 15 output arrays per case, 0 differing elements of 100848 (`shunn3_32`), 626320 (`csmag_32`), 33.5 million (128^3), 110.7 million (192^3). Host 4-thread build vs host serial: 0 differences in all four; two gfortran versions on two machines: 0 differences at 32^3.

- **Kernel time (run, partly synthetic: tiled input, serial gfortran baseline on a different shared machine;** median of 50 device-synchronised calls, 20 at 192^3; host 5 calls): 128^3 ten-kernel chain 4.9 ms on the device, 32.1 ms on one host thread, 27.8 ms on four (6.5x, 5.6x); per kernel 5.0x to 8.4x vs one thread (128^3), 4.5x to 7.7x (192^3). ### 7.5 Exit code 139 of the GPU harness (run, root cause found)
- **Cause (run, gdb backtrace on a short job, `results/gdb_exit139.log`):** the segmentation fault happens in `exit()` after `main` returned: the file-scope `std::map<std::string, Fld>` that holds all MultiFabs is destroyed by the static destructors after `amrex::Finalize()` has released the arenas, so `BaseFab::clear()` frees through an arena that no longer exists. ### 7.7 PoissonHybrid on fully singular problems: root cause (run; device and host, AMReX 99ddfda)
**Finding in plain language.** The hybrid solver is correct. For a closed box (all Neumann) or a periodic-in-x-and-y box with solid top and bottom, the pressure equation only has a solution if the right-hand side adds up to zero over the volume (the discrete compatibility condition). `FFT::Poisson` quietly throws away the part of the right-hand side that does not add up to zero; `FFT::PoissonHybrid` does not: it forces a solution by pinning the top layer, and when the right-hand side has a non-zero sum it solves a slightly different equation. The error is in the top layer: residual = (sum of the right-hand side over a column, i.e. nz times the mean) in that layer, which is exactly what was seen (mean 4.3e-5 times nz = 128 gives 5.5e-3). With a right-hand side of zero sum, `PoissonHybrid` is exact to round-off, on uniform and on stretched z. So the earlier failure came from the test right-hand side (random noise with a small non-zero mean), not from a defect in the transform or tridiagonal solve. It is an undocumented precondition and a missing safeguard in AMReX, not a wrong formula; the fix is on the caller side (remove the volume-weighted mean) or the small AMReX patch below.

**Code (`Src/FFT/AMReX_FFT_Poisson.H`, 99ddfda).**
- `FFT::Poisson`, all directions: the zero mode is left out of the division (`if (k2 != T(0)) { spectral_data /= k2; }`, lines 352 to 355), so the mean of the right-hand side is dropped and the solution gets a constant; incompatible data is projected silently.
- `PoissonHybrid::solve_z` (lines 636 to 847): singular means both offsets zero and both z faces Neumann (lines 699 to 702). The only special treatment is that the last diagonal of the z tridiagonal system is doubled for the zero mode, `if (i == 0 && j == 0 && is_singular) { bd(i,j,k) *= T(2.0); }` (lines 748 to 750 on the device branch, 811 to 813 on the host branch). That makes the matrix regular, which pins the zero-mode solution at the top layer. There is no mean removal. The modified last row reads `a p(nz-2) - 2a p(nz-1) = f(nz-1)`, so summing the zero-mode equations with the weights w_k (dz_k) gives `p(nz-1) = - sum w_k f_k / (w(nz-1) a)`: the pin is harmless (`p(nz-1) = 0`, the original equations hold exactly) if and only if the weighted sum of the zero-mode right-hand side is zero, and otherwise the equations are violated in the last row by the weighted mean times nz.
- Upstream test `Tests/FFT/Poisson/main.cpp` lines 67 to 71 subtracts the mean when no Dirichlet face exists (unweighted, uniform dz only), so the precondition is respected there and the stretched case is untested.
- Compatibility for stretched z is the dz-weighted sum, not the plain sum: `sum_k dz_k f_k = 0` (the finite-volume operator rows have `c_k dz_k = a_{k+1} dz_{k+1}`).

**Tests.** `fft/fft_sing.cpp` (`FFT::Poisson`, or `PoissonHybrid` with `Vector<Real> dz`), `fft/compare_sing.py` (independent numpy reference with the full discrete operator, finite-volume non-uniform z, eigen decomposition with a symmetrised z operator; singular mode dropped and means removed, weighted by dz), `fft/cases_sing.txt`, `fft/cases_sing_extra.txt`, `fft/run_sing_*.sh`, results in `fft/results/sing_table.md`. Grids `32^3` and `128^3`, dx = dy = 1/32; z spacing uniform, symmetric stretch (0.75 to 1.25 dx) and geometric stretch (dz_k = dx 1.01^k, ratio 3.6 at 128 cells). Right-hand sides: `raw` (non-zero mean), `zm` (weighted mean subtracted in the program), `anti` (point-antisymmetric, exactly zero sum), `zmu` (plain mean subtracted, stretched z), `mean` (raw plus 1). PASS means residual/max|f| below 1e-9 and error below 1e-9 relative to max|reference|. 170 cases per build: device as shipped, device with the patch, host as shipped, host with the patch; every case run once.
- As shipped: 134 PASS, 36 FAIL, device and host give the same verdict in all 170. Every FAIL is `PoissonHybrid` on a singular problem (PP,PP,NN; NN,NN,NN; PP,NN,NN) with a right-hand side whose weighted mean is not zero: `raw` (residual 1.4e-3 to 2.0e-2, error 1e-2 to 0.3), `mean` (residual 31 to 127), and `zmu` on stretched z (the plain mean is zero but the weighted one is not: residual 4.6e-4 to 8.7e-3, error 2e-3 to 0.2). `zm` and `anti` pass on all singular cases (residual 1e-15 to 2e-14, error 1e-14 to 1e-12), uniform, symmetric and geometric stretch. `FFT::Poisson` (uniform only) passes every case, also with a non-zero mean (it returns the solution of the mean-removed problem; with `mean` = 1 the residual against the compatible right-hand side is up to 8e-12 and the error up to 1e-10).

**Correct usage today (no patch).** Before `PoissonHybrid::solve` on a problem with no Dirichlet face (closed box, or periodic x and y with solid z), subtract the dz-weighted (volume-weighted) mean from the right-hand side, as the pressure backend's `remove_mean` does for `FFT::Poisson`. Plain-mean removal is wrong for stretched z. `FFT::Poisson` does not need it but cannot take stretched z.

**Which FDS cases are affected.** The backend as written (`pressure_backend/FFTBackend.cpp`) uses `FFT::Poisson` only, and `CommonLayer::remove_mean` removes the mean for singular components, so no current driver case is affected. It matters only when `PoissonHybrid` is chosen, which the plan needs for stretched z: (1) closed box (all walls solid, no open vent, no mesh-to-mesh interpolated face) with a stretched z grid, and a periodic-in-x-and-y channel or box with solid top and bottom on a stretched z grid: affected unless the weighted mean is removed first, and the existing `remove_mean` weight is one uniform cell volume, so it has to become dz-weighted for such meshes; (2) the same geometries on a uniform z grid are fine with `FFT::Poisson`; `PoissonHybrid` would be affected only if chosen for them; (3) any case with an open boundary or an interpolated mesh boundary has a Dirichlet face, so the problem is not singular and none of this applies; (4) a one-cell direction with Dirichlet remains a separate limitation (section 7.6).

### 7.9a `csmag_32` edge and corner RHOS cells: cause found (run, CPU only, scratch copy of the driver)
**Question.** Why do 368 cells (8 corners and 360 edge cells) of the `DENS_P` `RHOS` of `csmag_32` differ from FDS by up to 1.5e-4 while the interior is bit-equal? Candidates: the clip and redistribution after the density update, the route (`FDSTL_EXTGHOST`), or the flux values in edge ghost cells.
**Method (all run, one scratch copy of the driver with extra dumps; the driver tree was not edited; the patches are saved, `stage1/csmag_iso/patches/`, `stage1/wp1b/`).** `RHOS/ZZS` dumped just before `CHECK_MASS_DENSITY` in the same run as the kernel inputs; clip flags and `DELTA_RHO` printed for the 368 cells; the run repeated with `FDSTL_EXTGHOST=0`; the 8 corners tested apart from the 12 edges.
**Results.**
- **The clip is not the cause:** clip flags 0 and 0 for the box (limits 0.01 to 100, density 1.195), `DELTA_RHO` has 0 nonzero cells, and the driver's own pre-clip `RHOS` equals the stored truth exactly (0 of 32768 differ). The 368 differences exist before any clip.
- **Neither is the route or the edge-ghost flux:** with `FDSTL_EXTGHOST=0` the dumped `FX/FY/FZ` are bit-identical to `EXTGHOST=1` (including the edge ghosts), the wall `UVW_SAVE` agrees to 1.1e-16, and the pre-clip `RHOS` to 2.2e-16 (14 cells).
- **Cause:** FDS `DENSITY` sets `UU = U` and then restores the normal-face velocity of every `INTERPOLATED` wall from `UVW_SAVE` (`mass.f90:424-436`, the generated kernel `wall_uvw_interp`). The kernel chain was fed the dumped `U/V/W`. At face walls (5400) the dumped value equals `UVW_SAVE` to 1.1e-16; at the 240 edge walls per direction it differs by up to 4.5e-4 (x), 4.4e-4 (y), 4.0e-4 (z), and at the 24 corner walls by up to 2.6e-4. Emulating the restore on the dumped velocity: face walls only leaves 368 cells wrong; edge walls only leaves the 8 corner cells; corner walls only leaves the 360 edge cells; each of the three edge directions alone fixes its 120 cells; edges and corners together leave 0.
- **Confirmation with the generated kernel:** `wall_uvw_interp` (host serial) applied to the dumped `UU/VV/WW` with the same-run `UVW_SAVE`, then the `DENS_P` chain: `RHOS` **32768 of 32768 bit-equal** to FDS; serial equals 4 threads (host only, no device run).
- **Reconciliation of 7.1 and 7.9:** the statement "not comparable (FDS takes another path)" in 7.1 is withdrawn; the 7.9 observation (368 edge and corner cells) was right and has this cause. In a chain, `wall_uvw_interp` must run before the density kernels (it does in FDS and in the planned order, WP11/WP12).
- **`tg128` confirmed (run, host only; `csmag_iso/results/tg128_summary.md`).** A scratch-driver run of `tg128` (128^3, one box, 2 steps) wrote the wall table with `UVW_SAVE` for all 98,304 external walls (all interpolated; 95,256 face, 3,024 edge, 24 corner walls). The 465 differing `RHOS` cells (8 corner, 442 edge, 15 face-class cells; max 8.6e-14) become **0 of 2,097,152** when the normal-face value of every wall is restored from `UVW_SAVE` before the density chain. Per class: face walls alone leave 450 (8 + 442), edge walls alone leave 23 (8 + 15), corner walls alone leave 457 (442 + 15), so each class fixes its own cells. Serial and 4-thread outputs are bit-identical. The dumped face value differs from `UVW_SAVE` on 90,346 face, 2,896 edge and all 24 corner walls (up to 6.6e-14). No test machine run was needed.
Scripts and tables: `stage1/csmag_iso/` (`results/summary.md`, `results/tg128_summary.md`, `uvw_interp_check.py`, `run_tg128.sh`).

### 7.10c Device checksum in the harness check mode, the kernel shim, and the +0 / -0 rule (run, test-machine GPU, real wall tables)
**What was built** (`stage1/wallchk_block.inc`, included by `gen_wall.py` into the wall runner `s1w_gpu.cpp`; results `results/wallchk_summary.md`, `results/wallchk_runs.txt`): class `WallChk` holds UVW_SAVE, U_GHOST, V_GHOST, W_GHOST of the case. Before each of the 11 wall-kernel stages it refreshes (upload plus checksum issued, no sync, no copy-back); only with `S1_CHECK=1` does it also recompute the checksum from the device arrays, copy 8 bytes back and compare with the host fold (mismatch: message and exit code 3). Both modes do one deferred read at exit (exit code 4 on mismatch). Fault injection for tests: `S1_INJECT=host|reassign|flip|negzero` at stage `S1_INJECT_STAGE`.
**Results (run; `csmag_32` with 6144 walls and `tg128` with 98,304 walls; 22 launches of the runner, 3 timed repeats of each kernel, outputs of the kernels unchanged).**
- Clean runs: production 0 copy-backs during the run, exit 0; check mode 11 copy-backs, 0 mismatches of 11 stages, exit 0.
- Negative controls in check mode (host value changed without refresh, wall order changed without refresh, one bit flipped on the device, +0 on the host vs -0 on the device), 4 faults x 2 cases injected at stage 5: **8 of 8 detected at the injected stage, exit 3**; a bit flip injected at stage 11: detected in both cases.
- Production mode with the same faults at stage 5: **not seen during the run** (exit 0) and repaired silently by the next refresh; at stage 11 the deferred read at exit sees them (4 of 4, exit 4). Check mode on the first run and in CI is therefore required; the deferred read is a diagnostic only.
- Cost: refresh 16 us (6144 walls) and about 520 us (98,304 walls) in both modes (upload dominated, as in 7.10b); the check-mode verify adds 32 us and 254 us per stage (checksum kernel, copy-back, host fold).
- Superseded limit: the first version checksummed `WallChk`'s own copies while the kernel runners allocated their own buffers; the shim below removes that. The sign-of-zero point of 7.13a led to the explicit rule below.

**Shim: the kernels read the check object's own device arrays (run, test-machine GPU cc 8.9; `results/wallshim_runs.txt`, `results/wallshim_compare.md`).**
- `gen_wall.py` now takes the four wall-state arrays (`UVW_SAVE`, `U_GHOST`, `V_GHOST`, `W_GHOST`, all intent `in` in the 8 wall kernels that read them) from the `WallChk` device pointers when the check object is active, and does not allocate or free them in the runner. Because the kernels now consume the checksummed buffers, check mode also recomputes the checksum **after** each kernel (post-kernel verify) to show that a kernel did not write them.
- Clean check runs: 0 mismatches, 0 post-kernel mismatches on `csmag_32` (6144 walls), `tg128` (98,304 walls, reconstructed table, partly synthetic) and `dec2_obst_b0..3` (576 walls each; 12 stages each).
- The same injected faults, strict rule (host, reassign, flip, negzero): **8 of 8 detected at the injected stage 5, exit 3**; the post-kernel verify flags them as well (mismatches 1, post-kernel mismatches 1 in the injected run).
- **Wall-kernel outputs after the shim, bitwise (sha256 per output array): device = host serial = host 4 threads on 160 of 160 output arrays** (24 for `csmag_32`, 24 for `tg128`, 28 for each of the 4 `dec2_obst` boxes).
- Cost (median, test-machine GPU): refresh issue 12 to 16 us at 6144 walls and about 520 us at 98,304 walls; check-mode verify about 33 us and about 255 us per stage plus the post-kernel verify.
- Still a harness-level stand-in: in the driver the arrays are owned by the shim (WP10/WP11); only the pointer hand-over is shown here.

**The +0 / -0 rule, explicit in code (run; `stage1/zero_equal.h`, `zero_equal.py`, tests `test_zero_equal.py`, `zero_equal_test.cu`; `results/zero_equal_test_host.out`, `zero_equal_test_device.out`, `test_zero_equal_py.out`).**
- **Rule:** two doubles are equal iff they are bit-identical after mapping -0.0 to +0.0. Every other difference is a failure: 1 ulp, the sign change of a nonzero value, +0 against the smallest subnormal, infinities of different sign, and **any NaN on either side (even NaN against NaN with identical bits)**. Integer arrays: plain equality.
- **Helper (C++/CUDA, header only, namespace `ze`):** `canon_bits`, `is_nan_bits`, `equal_bits`, `equal`, `compare(a, b, n)` returning bytes-equal, values-equal, failures and NaN counts, `fold(...)` (order-sensitive fold of canonicalised bits), and device kernels `chk_kernel` (fold plus NaN count) and `cmp_kernel`. **Python:** `zero_equal.compare/equal/canon/fold`; the Python fold gives the same value as the C++ one (golden test).

### 7.12 Launch model of nvfortran K2 target launches (run, test-machine GPU)
Question: are our K2 launches (`target teams distribute parallel do` with `is_device_ptr`, no `nowait`, built with nvfortran 26.9 `-mp=gpu -gpu=cc89,nofma`) blocking or asynchronous, and what does that mean for the "syncs" and "streams per box" statements of the plan and for the order against AMReX streams and `cudaMemcpy`? Probe: `stage1/launch/` (Fortran kernels as in the generated code, a CUDA main; also a `nowait` variant), two runs, each test repeated 10 times.
- **K2 launches are blocking:** a kernel of about 285 ms made the call return after about 285 ms, and the following `cudaDeviceSynchronize` took about 3.5 us. A plain CUDA launch returns in about 1.6 to 3 us. A tiny blocking K2 launch costs 7.7 us including completion.
- **A K2 launch does not wait for other streams:** launched right after a kernel on another stream (non-blocking and default-flag streams) with no sync, it read stale data in 10 of 10 runs. The host must synchronise the stream before a K2 launch that reads data an AMReX stream wrote.
- **`cudaMemcpy`:** a device-to-host copy right after a long kernel on a non-blocking stream was stale in 10 of 10 runs; after a blocking K2 launch it was never stale (0 of 10), because the K2 launch has completed. Host order K2, stream kernel, K2 was correct (0 of 10 wrong).
- **`nowait` is not usable:** about 2.06 ms to issue each launch, plus a task wait; a `nowait` region followed by a blocking K2 reader of the same buffer without the wait saw an unfinished writer in 10 of 10 runs (the queues are unordered against each other).
- **Overlap:** 20 blocking small launches took 25.3 ms from 1 host thread, 26.5 ms from 2 threads (different buffers), 41 ms from 3 threads; blocking launches from different host threads do overlap on the device.
**What it means for the plan.** (1) A K2 launch is itself a host synchronisation point, so no extra sync is needed after a K2 launch; the sync that matters is the one **before** a K2 launch that consumes an AMReX-stream result. (2) "Streams per box" cannot be put on K2 kernels: K2 cannot be placed on an AMReX stream; overlap between boxes for K2 means one host thread per box, and only data-movement kernels written as K1 can be queued on the development machine stream. (3) The sync counts of the flux-hook review (finding 4: 2 syncs and 2 copies per kind and stage) were written for stream kernels; with K2 chain kernels the read-out is already complete when the host looks at it, so the sync that remains is for the K1 gather or pack kernel. (4) A `cudaMemcpy` ordered after a K2 launch is safe; ordered after a stream kernel it needs a stream sync. (5) The ruling that data-movement kernels may be K1 (proposed ADR-001 entry, `adr001-data-movement-kernel-entry.md`) follows from this. Not measured: K2 launches under several host threads on one box with AMReX streams active at the same time.

### 7.14 Box-batched radiation sweep launch layer (D-073): byte identity on SYNTHETIC boxes and the launch cost (run: host, and the cc 8.9 test-machine GPU)
**What was built** (`stage1/rad_sweep/`, README there). The launch layer holds the plane tables (`NPL`, `PLN`, `BOX_*BAR`) and the per-plane launch widths on the device, built once per regrid with the Radiation Lead's host helpers and uploaded once. It loops on the host over bands, updates, angles and planes as in addendum 1 section 3 of `docs/radiation/06-fr062-sweep-kernel-design.md` and calls the 11 blocking K2 kernels of the pinned file (s5-gen commit `a5e8f96cbf`, copied verbatim to `rad_sweep/pinned/`): per angle `max(NPL)+6` launches (46 + 6 = 52 for 16^3 boxes, 94 + 6 = 100 for 32^3), ONE launch per plane for all boxes of the level. The box-stacked `UII` and gray-gas `QR` kernels, which the addendum leaves to the driver layer, are in `rad_stack_k2.F90` (hand-written, arithmetic of radi.f90:4963 and 4982, ascending sum over the slices). ## 8. Risks
Host/device hand-offs (host wall routines read and write the same FABs every stage; a stage's whole field set costs 4.5 to 33 ms at 128^3 and 15 to 111 ms at 192^3 one way, 9 to 13 times the kernel time, section 7.8); unified-memory page migration (managed memory is a debug option only, ruling a); per-step gather of wall tables; device FFT through AMReX FFT/cuFFT (periodic and even/odd boxes verified, sections 7.4 and 7.6; plan set-up costs 50 to 80 ms once); no-FMA and fast-math-off in every translation unit (K2 `nofma`, nvcc `--fmad=false`, `AMReX_CUDA_FASTMATH=OFF`, host `-ffp-contract=off`); K2 kernels are not idempotent and not callable from several threads on one box (OpenMP tiling needs disjoint boxes); nvfortran reassociates unparenthesised sums, so the host reference stays gfortran; `__int128` fixed-point sums on the device unchecked (only the switchable exact-sum option needs them, D-053); kernel bounds are tied to one box per mesh with local origin 1 (D-052); host-only `fill_omesh` copy and wall-routine hand-offs dominating the step; PoissonHybrid needs a compatible (volume-weighted zero-mean) right-hand side when the problem is fully singular (section 7.7); a Dirichlet condition on a one-cell direction is ignored by the FFT solver (section 7.6); the SOLID mask copy must follow `CELL%SOLID` (the kernels' mask works, section 7.9b); `wall_strain_rate` and `wall_us_pred` now do real work on an obstruction case (section 7.10a) but have no FDS truth, so only device = serial = 4-thread equality is shown; the real-data tests use substitutes for some arrays (section 7.9); the edge and corner density differences of `csmag_32` are explained (section 7.9a: `wall_uvw_interp` must run before the density kernels, so the wall-kernel order matters for WP11 and WP12); K2 launches block the host and do not wait for AMReX streams (section 7.12), so every mixed K2/stream sequence needs an explicit stream sync before the K2 launch and K2 cannot overlap boxes on streams; WP9, WP9b and WP12 cannot be tested by the periodic single-box case; flux hooks are host-only today (section 7.11); at 32^3 and below, and for one box of 16x1x16, the device is slower than the host (launch floor), so small boxes should stay on the host or be batched.

## 11. Wall-seam fold-in
How the measured wall results change the plan (details in section 7.10, packages WP8, WP10 to WP12):
1. The four host-resident wall-state arrays are copied to the device as four plain copies by a refresh that fires before every stage, at a regrid and at `REASSIGN_WALL_CELLS` (WP10, approved; D-061, W2; section 7.10b): 0.32 to 0.39 ms at 98,304 walls, 30 to 38 us at 6144 walls; no packing and no pinning needed (pinned saves about 45% at 98,304 walls but pinning costs about 0.2 ms per MB once, so pin only if the upload shows up in the step profile).
2. The device checksum replaces the host `CHECKSUM` assertion on the uploaded arrays (14 us against 155 us at 98,304 walls, bit-equal, order-sensitive); it is computed at every refresh and its 8-byte copy-back and comparison with the host value run only in check mode (first run and CI), because that copy-back is the one sync per stage.
3. Wall kernels run on the device wall tables with `NWE`/`NWI` (WP11): identity lists today; the tables are static between geometry events and are re-gathered with WP8 after `REASSIGN_WALL_CELLS`. WP11 is sequenced after the generator's `WLIST`/`NWL` indirection (W1), which the Generator Engineer applies; the wall kernels are re-timed afterwards. `wall_uvw_interp` must run before the density kernels (section 7.9a).
4. Scatter and gather (WP12): outputs host routines still read cross back only as needed (`UN_WALLS`, `B1_*`, ghost-cell values, `HS`); the package starts with the per-array writer/reader table and the edge/corner write-collision check, no code before it; ordering against the ADV flux hook per review finding 5 (the `UVW_SAVE` restore needs the upload first).
5. The obstruction case with `SOLID_BOUNDARY` walls (`NWI` > 0) now exists (section 7.10a): both kernels that did nothing before change elements and are bit-equal device = serial = 4-thread; they still have no FDS truth. The wall-table dump is a draft patch for Role 1 (WP1b).
