# FDS-AMR requirements

Owner: Spec & Program Lead · Status: draft v0.4.21 (2026-09-26; changelog in README.md) · Source pin: FireX 36975d765f on branch `FDS-AMReX` (this repository; also on github.com/marcosvanella/fds, D-037)

## 1. Conventions

- IDs: **FR** functional, **NFR** non-functional, **IR** interface. IDs are never reused. Retired requirements keep their ID and are marked *retired*.
- Each requirement gives a statement, rationale, verification method (**T**est, **A**nalysis, **I**nspection, **D**emonstration) and an acceptance criterion.
- **proposed** = a number suggested here that nobody has confirmed yet. **TBD(owner)** = the named lead supplies the value. Neither kind is a commitment until the project owner approves it.
- **ASSUMPTION** = a scope assumption to be confirmed (charter §4, §9).
- *Phase* refers to roadmap.md.

## 2. Definitions used in acceptance criteria

### 2.1 Baseline

Every citation names the milestone pin it refers to; until the first re-pin, all citations in these documents refer to `36975d765f` (R-44).

### 2.1a Pressure comparison tolerance eps_H
For comparisons between two solvers on the **same discretisation** (e.g. FR-002: baseline GLMAT vs composite single-level solve), `H` shall agree to **eps_H = max(1e-8, 2.4e-12·N²)**, N = largest cell count per direction (the floor 1e-8 governs up to N ≈ 64): volume-weighted mean removed, relative L2. It is valid only for a single solve on frozen input. It does **not** apply to multi-step run outputs, where differences accumulate; those use the T2/T3 classes (§2.2). It is derived from UGLMAT's stopping test ‖r‖ ≤ 1e-12‖b‖ (pres.f90:4828-4838; imkl.f90:238-240) and a Poisson condition number growing like N² (Pressure Lead, 2026-09-25; N² form added the same day; D-012). Coarse-fine comparisons against UGLMAT are not same-discretisation, and eps_H does not apply to them (FR-016(c)).

### 2.2 Tolerance classes
| Class | Definition |
|---|---|
| T0 bitwise | Byte-identical output. Used for (1) kernel-level bit-parity with single-mesh FDS: the output fields of an explicit kernel (mass, velocity predictor, divergence) on frozen input, compared array by array (D-022); and (2) self-comparisons of the same code or of FDS with itself (restart vs continuous, IR-006, run-to-run reproducibility, FR-005): byte-identical `CHID_devc.csv`, `CHID_hrr.csv` and `CHID_mass.csv` (when present), with the timing/version columns excluded (by name pattern plus a per-case list, e.g. DEVC `QUANTITY='CPU TIME'`). Same rank count, `OMP_NUM_THREADS=1`. Evaluated on derived V&V copies of the inputs with `&DUMP SIG_FIGS=17` added, created under `(local V&V run directory)/`, never edits to the repo. FDS's default `SIG_FIGS=8` (read.f90:2374) does not make byte-identical CSVs bitwise (vv/test-plan.md §9.2, D-1). |
| T1 tight | Same uses as T0. For every kernel output field on frozen input, or every column of the DEVC, HRR and mass CSVs at every output time: \|x − x_base\| ≤ 1e-10 · max(\|x_base\|∞ over the column, 1e-30) (proposed). `OMP_NUM_THREADS=1`. Evaluated on the same `SIG_FIGS=17` derived copies as T0, because 8 significant figures cannot resolve 1e-10 (D-1). |
| T2 verification | The case meets the acceptance metric the FDS verification process applies to it (Verification Guide / `Utilities/Python` verification script). Its error metric e is no worse than baseline's: e ≤ (1 + m)·e_base + 0.1·Tol_FDS, where Tol_FDS is the dataplot `Error_Tolerance` or script limit (absolute floor for near-zero metrics, D-9) and m = 5%. Chaotic cases (fires/LES): m = max(5%, 3σ), σ = relative spread of the metric over repeat baseline runs (GNU/Intel × two rank counts). The FDS criterion e ≤ Tol_FDS always holds. Plot-only / convergent-series rows: observed order ≥ min(p_base, nominal) − 0.1, and finest-grid L2 error per the rule above. Provisional, calibrate against measured FireX baseline (vv/test-plan.md §9, R-1). |
| T3 physical | Case-specific tolerance on physical quantities for multi-level vs uniform-fine comparisons (and AMR-mode rank comparisons). Time-averaged (window ≥ last 50% of the run, ≥ 10 puffing periods): plume centreline temperature rise and vertical velocity within 10% at each probe height in the refined region; integrated HRR and burner mass-loss rate within 2% (1% where HRR is prescribed); compartment layer height within 5% or one fine cell (absolute floor), layer temperatures within 5%; turbulent point probes mean within 10% and RMS within 25%, never instantaneous values. Analytic cases: FR-014. Discrimination rule, always: \|AMR − fine\| ≤ 0.5·\|coarse − fine\| for the same quantity; a case where coarse and fine barely differ is not a T3 case. Calibration: max(value above, 2× the measured GNU-vs-Intel spread of the uniform-fine run), capped by the discrimination rule. Provisional, calibrate against measured FireX baseline (vv/test-plan.md §9, R-2). |

**Bit-parity scope (D-022).** T0 and T1 against baseline FDS apply **only to explicit kernels on frozen inputs** (mass, velocity predictor, divergence), and only against **single-mesh** FDS: the committed single-mesh input, or a derived single-mesh copy of a multi-mesh input (A-24). Whole runs, single-level ones included, match FDS only within tolerance (T2) after the first pressure solve, because Crayfishpak (`pois.f90`) is replaced by `amrex::FFT::Poisson` (uniform level 0) or MLMG, and neither reproduces Crayfishpak's floating point; porting Crayfishpak per box was rejected (D-021). Multi-mesh FDS is not a bit-parity reference even for kernels: FDS averages face-normal velocity at every mesh-to-mesh face, same-resolution ones included (`MATCH_VELOCITY`, velo.f90:2669, 2732-2733; called at main.f90:411, 914, 1120), and `DENSITY` restores the saved values (mass.f90:429-434, 601-606). AMReX level-0 box boundaries follow `max_grid_size`, `blocking_factor` and load balance and change with rank count, and `FillBoundary` copies exactly, so emulating `MATCH_VELOCITY` at box faces would make results rank-dependent. Multi-level runs are never compared bitwise with multi-mesh FDS (D-023). One exception: FR-016(a), a step-1 component check of coarse-to-fine ghost fill against the multi-resolution FDS input, which has no single-mesh equivalent. eps_H (§2.1a) still applies to a single solve on frozen input. Optional debug mode, not a production requirement: pin the `BoxArray` to the FDS meshes and run the unmodified FDS routines at those faces to get multi-mesh parity. Open item (IR-007, A-34): the direction-split face loops stop evaluating FX/FY/FZ on tangential rows J=0 and K=0. Within `mass.f90` nothing reads those rows (the flux users at mass.f90:448 and :625 sit inside `K=1,KBAR / J=1,JBAR / I=1,IBAR` loops, 443-445 and 620-622), so ZZ/RHO parity on the core path is unaffected. Until A-34 closes, the frozen-input comparison excludes `STORE_SPECIES_FLUX` and CC_IBM cases.

## 3. Uniform-grid equivalence mode

**FR-001 Single-mesh equivalence.** With AMR compiled in and zero refinement levels, the code shall reproduce baseline FDS on single-mesh inputs.
- Rationale: isolates data-structure/driver regressions from AMR numerics (D-002).
- Verification: T. Acceptance: explicit kernels (mass, velocity predictor, divergence) on frozen input match single-mesh FDS at T1, T0 per Q1. Whole runs of all single-mesh anchor cases meet T2 against baseline: after the first pressure solve bit-parity is infeasible, because `amrex::FFT::Poisson` or MLMG replaces Crayfishpak (D-021, D-022). Phase 2.

**FR-002 Multi-mesh uniform equivalence.** With zero refinement levels, a multi-mesh input whose meshes all have the same cell size shall run as one AMReX level (one box per `&MESH`, or re-boxed per IR-004) and match the baseline reference.
- Rationale: a composite single-level pressure solve removes interface velocity error. The right reference is therefore baseline with `SOLVER='GLMAT'`, which the User Guide says produces the same pressure solution as FFT on a single mesh (FDS_User_Guide.tex, GLMAT item, line 9452; unchanged in the FireX Manuals tree), or the equivalent single-mesh input.
- Verification: T. Acceptance: explicit kernels on frozen input match baseline run on an equivalent single-mesh input (committed or derived, A-24) at T1, T0 per Q1. Whole runs meet T2 against that single-mesh input and against the multi-mesh baseline with the default FFT and with GLMAT (D-022). `H` from one solve on frozen input agrees with baseline GLMAT within eps_H (§2.1a); this single-solve check is unchanged. Phase 2; the first case is `shunn3_4mesh_32` at the M2a demo (D-006): bitwise explicit-kernel checks on frozen input against single-mesh FDS, full steps within tolerance against single-mesh and 4-mesh FDS. The earlier full-run "T1 against baseline GLMAT" is dropped, which resolves V&V's objection (vv/test-plan.md §9.2, D-3; README D-018).

**FR-003 Verification-suite non-regression.** In uniform mode, every FDS verification case inside the supported feature set that passes on baseline shall also pass. Stretched (TRN) inputs are outside the supported set in every mode and stay FDS-only (IR-002; ADR-002 v0.2.1). FR-006 extends the coverage to refined variants of in-scope features.
- Verification: T, at two frequencies. Tier 1+2 set (163 runs, about 90 min sequential / 40 min packed) at every phase exit. The full firebot-listed suite restricted to ≤ 8 ranks (870 of 884 active cases; about 15–30 h sequential model estimate, an overnight-to-weekend batch on an idle machine) at Phase 2 exit and Phase 10. The 14 cases that need 9–64 ranks are recorded exceptions unless more compute appears (Q6). Provisional, calibrate against measured FireX baseline (vv/test-plan.md §9, R-3). Acceptance: 100% pass under T2; each exception is recorded in `docs/vv/` and approved by the project owner. Phases 2, 10.

**FR-004 Explicit rejection of unsupported features.** When an input combines refinement (max level > 0) with a feature outside the supported feature set, the run shall stop during setup with an `ERROR(nnn)` message that names the feature. It shall not run silently. Deferred features (owner decisions D-033, and D-042, 2026-09-26; deferred, not permanently dropped): GEOM/CC_IBM (FR-044), HT3D and `CYLINDRICAL` meshes. `TUNNEL_PRECONDITIONER` is not rejected: in AMR mode the keyword is accepted, a setup warning is logged and it is ignored (D-041). Stretched meshes are rejected by the AMReX code in every mode (IR-002).
- Verification: T (one negative test per excluded feature). Acceptance: each negative test exits with `SETUP_STOP` and the expected message. Phase 3 onward.

**FR-005 Decomposition, rank and thread independence.** Results of the AMReX code shall not depend on the level-0 box split, rank count or thread count beyond the following limits:
- (i) Explicit stages that are reduction-free are byte-identical across level-0 box split, rank count and OpenMP thread count, on frozen inputs or, given identical stage inputs, in runs without pressure zones. Thread-count independence of reduction-free stages is part of the requirement, not only box-split and rank independence (Chief Architect). An explicit stage that uses an OpenMP reduction is byte-identical across box split and rank count only at a fixed thread count, as in (iv).
- (ii) With pressure zones, the zone integrals `DSUM`/`PSUM`/`USUM` (`EXCHANGE_DIVERGENCE_INFO`, main.f90:2028-2054; `MPI_ALLREDUCE` sums at main.f90:2038-2040; they feed `D_PBAR_DT`, read by mass.f90:548, 730) and the mean-removal pressure gauge use exact, order-independent summation (e.g. fixed-point int128 accumulation with a fixed scale, then conversion to floating point), so they are independent of box split, rank count and thread count. The exact accumulation starts at the per-cell/per-box sum, not only at the Allreduce: 68 of the 91 order-dependent floating-point rows are per-process loops over meshes before the MPI call, and regridding also changes the cell order within a box (`inventory/README.md`, global reductions; `inventory/global_reductions.csv`). AMReX has no reproducible reduction (`ParallelDescriptor::ReduceRealSum` is a plain `MPI_Allreduce`). Cost is negligible: a few scalars per zone per step. Owner: AMReX Integration Lead. All global reductions are catalogued (A-25 closed): 259 rows, 91 order-dependent floating-point sums feeding 13 quantities (DSUM/PSUM/USUM; `RAD_Q_SUM`/`KFST4_SUM`, main.f90:1760-1761; HVAC nodes; device statistics feeding controls; synthetic-eddy means; setup-time areas and volumes). Each of these physics-feeding sums uses the same exact accumulation. DT and the iteration tests use MIN/MAX and are order-independent.
- (iii) The pressure solution agrees within eps_H (§2.1a) across box split and rank count: MLMG bottom-solver dot products and norms are rank-order-dependent reductions, and the box layout changes the coarsening depth. P2 (64³, Neumann and periodic only; 1/2/4 ranks × max_grid_size 32/16, every path including FFT): worst rel. L2 2.4e-16, not bitwise (`amrex/p2-findings.md` §3). Dirichlet is untested (V&V-plan gap, A-39).
- (iv) At a fixed rank count, fixed OpenMP thread count and fixed box layout, with `OMP_DYNAMIC=false`, runs are bitwise reproducible run to run. The FFT path plans with `FFTW_ESTIMATE` (`AMReX_FFT_Helper.H:542-1691`). AMReX CPU reductions (`MultiFab::Dot`, MLMG and gauge norms) use OpenMP `reduction(+:)`, whose combine order is unspecified, hence the fixed thread count. The exact sums in (ii) are order-independent and unaffected. P2: 3 repeats bitwise for every pressure path at 4 ranks × 1 thread and 2 ranks × 2 threads (64³ Neumann, max_grid_size 16 only; `amrex/p2-findings.md` §4; other boundary types are a V&V-plan gap, A-39).
- (v) Setup-time areas and volumes (D-028): the driver computes `FDS_AREA` and `AREA_ADJUST`, and every setup-time area and volume sum in `inventory/global_reductions.csv`, over the whole domain with the exact fixed-point sum. This reproduces single-mesh FDS, the bit-parity reference (D-022), and is decomposition-independent. FDS's per-mesh accumulation is deliberately not reproduced: `MULTIPLIER%FDS_AREA` is accumulated per mesh and never reset or reduced (init.f90:366-424), an upstream defect now confirmed by runs (Legacy Mapper, FireX 36975d7 and `ce1f659`; MULT-voxel cylinder R=H=0.1 m): 1 mesh exact; 2 meshes on 1 process top ×0.75, side ×1.5; 2 meshes on 2 processes top ×1.0, side ×2.0; moved split top ×0.87, side ×1.7; two cylinders sharing one MULT on 1 mesh ×0.5. Causes: per-MULT, per-mesh accumulation never reset or reduced across processes (init.f90:366-426), and inconsistent target areas (top counts only the in-mesh part, side the whole cylinder; read.f90:10962, 10966); only CYLINDER shapes are adjusted (read.f90:10950). Draft upstream issue #1 in `inventory/upstream_issue_candidates.md` (not filed). Verification: T on a shaped multiplied OBST split across 1, 2 and 4 boxes (`vv/test-plan.md` §5.3 (v-a)-(v-c)). **Acceptance (decided, replacing "reproduces single-mesh FDS"):** AMR results (`AREA_ADJUST` per face class, resulting fuel MLR, zone and gas volumes) are bitwise identical across AMR layouts, rank counts and thread counts (T0), and within 1e-10 relative of single-mesh FDS (T1), because an exact sum cannot always match FDS's sequential floating-point sum bit for bit; if a case misses 1e-10, the report gives the face/cell count so the float-sum error of FDS itself can be judged. The values are observed through the setup report of FR-075. **Negative input:** the committed OBST-cylinder FM_Burner inputs (e.g. `FM_15cm_Burner_CH4_2cm.fds`) run by FDS with the burner meshes on one process deliver 0.5208 (25/48) of the specified fuel flow, against exactly 1.0 with one mesh per process or a single mesh (`vv/fm_burner_area_check.md`); FDS multi-mesh is therefore not a reference, and the AMR result must be 1.0 in every configuration (R-24).
- Acceptance (bitwise tests against FDS; V&V): any bitwise comparison with FDS (D-022, and (i) against single-mesh FDS) replays FDS's exact T and DT sequence, including the last-step adjustment of about 20 machine epsilons, `DT = MAX(T_END-T+TWENTY_EPSILON_EB,DT_END_MINIMUM)` when `T+DT+DT_END_FILL > T_END` (main.f90:719; `DT_END_FILL` = 1e-6, cons.f90:429), and the modified DT that a restart carries (`amrex/p1-findings.md` §5; P1's `p1.t0`/`p1.dt`/`p1.t_end` do this).

For clip-affected cases the reference is single-mesh FDS, because FDS multi-mesh clipping is itself layout-dependent. P1 evidence: without the rewrite, SUPERBEE on the FDS initial field differs by 5e-5 across max_grid_size 32 vs 8 (`amrex/p1-findings.md` §6.2); all non-clipping cases are bitwise (§6). With the gather clip (A-37 closed, §13) SUPERBEE is bitwise across box splits and ranks and against single-mesh FDS.

**FR-010 Static refinement.** The user shall be able to specify fixed refinement regions (boxes) per level, up to a maximum level.

Support at least max level 2 with ratio 2 (proposed). Supported refinement ratios per level: 2 and 4 (pressure/README.md Q12). Ratio ≤ 4 because MLMG's coarse-fine tangential interpolation asserts ratio ≤ 4 (AMReX `Src/Boundary/AMReX_InterpBndryData.H:186-188`), so ratio 8 is not available with the composite solve (FR-030); an FDS input with an 8:1 mesh abutment would need an intermediate level. Input to ADR-002 (Pressure Lead, 2026-09-25); in ADR-002 v0.2 (2026-09-25). FDS itself has no explicit mesh-to-mesh cell-ratio bound: the only limit is implicit, tangential ratio < 40, from where `INIT_WALL_CELL` places its probe points (init.f90:3161; the ERROR(431) span test at init.f90:3194-3208 fails beyond it; derived, not run). `ALIGNMENT_TOLERANCE` (cons.f90:598) is the span-test tolerance, not a ratio cap. Confirmed by the Legacy Mapper (inventory complete): FDS has no coded maximum; fine faces must tile coarse faces within 0.001 (init.f90:3184-3226, cons.f90:598); powers of two are not required and tangential ratios may differ; the probe limit r < 40 (init.f90:3161-3163) is implicit and not run; the User Guide advises at most 4:1 (FDS_User_Guide.tex:1127). The cap of 4 excludes nothing; the {2,4} restriction excludes FDS inputs with 3:1 or direction-dependent ratios, which are rejected in AMR mode (pressure/README.md Q12; init.f90:3184-3226). Ratio 3 passes MLMG's assert (3 ≤ 4) but is untested elsewhere; a P2 check for it is added only if a reference case needs it, and the supported set is not widened before then. Which FDS inputs have such ratios: A-33 (`inventory/mesh_ratio_cases.csv`). Phase 3.
- Acceptance (ratio rejection; Pressure Solver Lead and Legacy Mapper): AMR mode rejects an unsupported ratio at input time with an error naming the mesh pair and the ratio. Verification: T with a 3:1 input and a direction-dependent input.

- Acceptance (blocking-factor check; Integration Lead): the same input-time check reports a blocking-factor mismatch next to any ratio error, naming the mesh or level and the numbers, instead of letting AMReX abort (`AMReX_AmrMesh.cpp:1259`, "domain size not divisible by blocking_factor"): a level-0 domain not divisible by the level-0 blocking factor, or a fine patch not aligned with the level-1 blocking factor. Single-cell direction (2-D input in a 3-D build; Integration Lead; **provisional until the P2 `int_1to2`-geometry case confirms it (A-49; formerly the second half of A-38, closed)**; also in ADR-002 v0.2.1, which cites the same `AMReX_MLLinOp.H:89`, :951 and :1218-1219): MLMG holds one refinement ratio per AMR level for all directions (`m_amr_ref_ratio`, AMReX `Src/LinearSolvers/MLMG/AMReX_MLLinOp.H:891`, set from `rr[0]` at :1223). The only exception is a hidden direction set with `LPInfo::setHiddenDirection` (:89), which gets ratio 1 (`AMRRefRatioVect`, :951; the level ratio is then taken from a non-hidden direction, :1218-1219) and is not coarsened by multigrid (:1177). A 3-D build one cell thick in y therefore needs `amr.ref_ratio_vect = 2 1 2`, a y blocking factor of 1 (`amr.blocking_factor_y`, `AMReX_AmrMesh.cpp:311-315`) and `setHiddenDirection(1)`. - Acceptance (MLMG coarsening warning; Pressure Solver Lead, corrected by Integration Lead and Chief Architect): the input-time check prints a WARNING (not an error) when the level-0 domain cell counts cannot be halved at least 3 times in every direction, and prints the resulting coarsest MLMG grid size. **FR-016 Static two-level equivalence with FDS multi-resolution meshes.** A static two-level hierarchy that reproduces an existing FDS input with abutting meshes of different resolution (ratio 2) shall reproduce baseline FDS's coarse-to-fine interface ghost fill for transported and diffused fields (ρ, ρY_α, temperature, and ghost-averaged properties such as `MU`, `KRES`, `D`/`DS`). In the fine-to-coarse direction it shall instead use `average_down` plus flux-register refluxing. `H` and post-projection face velocities are excluded from the ghost-fill match, because the composite solve couples levels through its own interface stencil (FR-030).
- Rationale: FDS already couples meshes of different resolution through `EXTERNAL_WALL(IW)%IIO/JJO/KKO_MIN:MAX` ranges and averages `OMESH(NOM)` data into ghost cells (e.g. velo.f90:516-546, wall.f90:321, turb.f90:2284, vege.f90:677; Legacy Mapper, 2026-09-25). One loop serves both directions: a one-cell range gives piecewise-constant copy (coarse-to-fine) and a multi-cell range gives averaging (fine-to-coarse). The direction for each mesh pair is therefore fixed where those ranges are computed. `docs/inventory/interface_averaging_sites.csv` records it (sites may be `both_runtime`). Coarse-to-fine should be reproduced exactly by AMReX `FillPatchTwoLevels` with `PCInterp` (`Src/AmrCore/AMReX_Interpolater.H:420`; Integration Lead, 2026-09-25). Fine-to-coarse has no ghost-fill equivalent in AMReX and becomes restriction plus refluxing.
- Reference: baseline with `SOLVER='UGLMAT'` and HYPRE. It is the FDS solver that supports refinement and matches normal velocity exactly at mesh boundaries (FDS_User_Guide.tex:9455; Pressure Lead, 2026-09-25). `GLMAT` is the reference only for single-level multi-box tests (FR-002). The `.out` header of a UGLMAT run prints `Solver: UGLMAT` without the library (dump.f90:3174, unlike ULMAT), so HYPRE is confirmed from the `SOLVER='UGLMAT HYPRE'` keyword path (func.f90:7154-7159) and the build provenance (A-38).
- Verification: T on `Adaptive_Mesh_Refinement/ns2d_16_int_1to2_refinement.fds` only (13 meshes: a fine 16×16 patch abutting 12 coarse 4×4 meshes, ratio 2), with first-step ghost-cell dumps on both sides of the interface (unit-level), then full runs. There is no interface spike: coarse-cell errors next to the patch lie between the single-level 32³ and 64³ errors.

**FR-025 Species realizability across level operations** (proposed; AMR Species & Combustion Lead, `combustion/01-species-combustion-amr-spec.md` §2, §6, draft). - Owner: AMR Species & Combustion Lead. Verifier: AMR V&V Lead.

## 6. Pressure solve across levels

**FR-030 Composite solve.** The Poisson equation for H shall be solved as one composite problem across all levels at both pressure solves per step (predictor and corrector), replacing per-mesh FFT plus interface iteration in AMR mode.
- Rationale: ADR-002 leaning (open). The FFT path (`PRESSURE_SOLVER_FFT`, pres.f90:318) needs one tensor-product block per solve and couples blocks only through iterated Dirichlet values (pres.f90:97-143; main.f90:1623-1743).
- Implementation constraint (Integration Lead, 2026-09-25; AMReX checkout `(local AMReX checkout)`): a cell-centred, multi-level, variable-coefficient solve can be driven from Fortran. `amrex_abeclaplacian` exposes `set_acoeffs`/`set_bcoeffs` (`Src/F_Interfaces/LinearSolvers/AMReX_abeclaplacian_mod.F90:15-16`), so the variable-density (1/ρ) form is available, and MLMG can use HYPRE as bottom solver (`AMReX_multigrid_mod.F90:9-14`). A nodal projection, `MacProjector`, EB operators or an overset/obstruction mask in the operator have no Fortran bindings and force C++. Tensor-coefficient operators have not been confirmed (TBD(Integration Lead)). The language of the FR-030 implementation therefore follows ADR-003 (EB or not), via ADR-001. Team leaning (ADR-001): the pressure path sits outside the per-box `POINT_TO_MESH` shim either way.
- Input to ADR-001 (not a C++ mandate): the uniform level-0 solver `amrex::FFT::Poisson` (FR-037) is C++ only (C++20 templates, no `F_Interfaces` bindings), so a Fortran-driver Option B would have needed an `extern "C"` wrapper (100-200 lines); Option B is now rejected (D-027). A GPU path exists through cuFFT (CUDA, the required backend, Q11 (a)); AMD/HIP is out of scope (D-027, owner amendment).
- Algorithm (Pressure Lead, 2026-09-25): the FDS step is algebraically a MAC projection with potential H, with β = dt in the predictor (velo.f90:1603-1630) and dt/2 in the corrector (velo.f90:1723-1751). With a global dt and a composite solve, no synchronisation projection is needed (R-05 is a subcycling risk only). The interface pressure iteration disappears. The baroclinic iteration stays in every case (FR-036), and the solid iteration stays only if immersed-boundary forcing is kept (FR-035).
- Solver rules (D-032; Chief Architect; ADR-002 v0.2): MLMG at `setMaxOrder(2)` (FR-039); exact mean removal before every singular solve, composite over uncovered cells per pressure zone, and the driver's standing true-residual check (FR-039); coarse C/F (and covered) face fluxes from `MLMG::getFluxes` are always overwritten with `average_down_faces` of the fine fluxes before the projection (`pressure/01-amr-mapping-spec.md` §C.2), because P2 found the raw coarse fluxes first-order wrong (`amrex/p2-findings.md` §2.2), while the composite operator itself matches the fine-flux sum to 1.8e-14; HYPRE is a bottom solver only, and diagnostic whole-solver use sets `hypre.adjust_singular_matrix=1` in the defaults (BoomerAMG alone diverges on closed domains otherwise, §8; AMReX_HypreABecLap3.cpp:487); on GPU, MLMG's own bottom solver stays the default (NFR-043).
- Verification: I + T. Acceptance: design approved in ADR-002 and the pressure memo; FR-031/032 met. Phase 4. Status: depends on ADR-001/ADR-002/ADR-003.

## 7. Obstructions and immersed boundaries

**FR-040 OBST on refined levels.** Rectilinear OBSTs, including thin (zero-thickness) obstructions, which must work with refinement (owner decision, D-033), shall be represented on every level that intersects them, with the following snap rule (proposed, D-009; details in spec-responses.md (f)):
- R1: each level snaps OBSTs with the unchanged FDS rule, using that level's dx and the level-0 origin. The rule is nearest-face `NINT` (read.f90:11157-11162); collapse to zero thickness below 0.25 cell (read.f90:11174-11215); `THICKEN` to one cell (read.f90:11167-11173, 11034-11039); discard if zero-thickness in ≥ 2 directions (read.f90:11218-11224); `THIN` flag below 0.5 cell (read.f90:11315-11317). Level 0 is therefore identical to baseline. This includes two upstream slips in the thin-OBST collapse branch (`THICKEN_DIR` off), confirmed by the Legacy Mapper (A-20 closed): the y snap at read.f90:11193 uses `GINV(XB3-XS,2,NM)` (x origin `XS` instead of `YS`), and the z snap at read.f90:11210 compares `REAL(OB%I1)`/`REAL(OB%I2)` but assigns `OB%K1`/`OB%K2` (also in `ce1f659` at read.f90:11060, 11077). They can pick the wrong face for sub-cell OBSTs collapsed in y or z. A third confirmed on FireX: read.f90:11176 subtracts an integer index from a length in metres (derived by reading). All three are logged in `inventory/uniform_grid_assumptions.csv` as behaviours level 0 must reproduce exactly.
- R2: in covered regions the fine mask is authoritative. `average_down` averages gas children only, and a coarse cell with all children solid is solid.
- R3 (R3-T, D-009 amendment; Chief Architect ruling, final, `adr/drafts/rulings-FR040R3-FR034.md` §1): no mismatch on coarse-fine interface faces, and inside the interface band (coarse cells within one coarse cell of the C/F boundary, covered and uncovered) the fine face mask is the exact refinement of the coarse face mask: a coarse face is a wall exactly when all its r² fine subfaces are walls (T1), and no fine wall face lies on a fine face plane interior to a coarse cell of the band (T2). Static FDS multi-resolution inputs that violate R3-T stop at setup with an error naming the OBST, both levels, both snapped planes and the C/F plane. Dynamic runs tag the whole footprint of every OBST whose R1 snap differs between levels plus one coarse cell, or keep it off the finer level; if that exceeds `MAX_LEVEL` or memory, stop. Masks, the band check and the zone check are rebuilt after every regrid; a failure after a regrid stops the run. Validity checks (ERROR(421)/(422), `THIN`) are evaluated on the owning level. **IR-007 P1 / device kernel interface.** (Chief Architect and Integration Lead; loop ranges and fused nests agreed with the Legacy Mapper.) "Unmodified `mass.f90`" holds only for the CPU shim. Both GPU variants of a kernel (restricted C++ `ParallelFor` and Fortran with simple OpenMP `target` offload, NFR-044; owner decision, ADR-001 v0.3) share one interface:
- Every field in `inventory/kernel_footprint_mass.csv` is passed as an explicit-shape argument. The kernel reads no module pointers (402 remapped by `POINT_TO_MESH`, `inventory/point_to_mesh_pointers.csv`) and no runtime globals (`inventory/module_globals.csv`) (R-35).
- Device data (ADR-001 v0.3, Chief Architect): AMReX field data is never mapped. Kernel wrappers take explicit-shape dummy arrays declared `has_device_addr` on the `!$omp target teams loop` (primary); `map` is allowed only for small host scalars. If the first nvfortran compile (A-31) rejects `has_device_addr` on Fortran dummy arrays, the fallback is `is_device_ptr` on `type(c_ptr)` arguments with `c_f_pointer` inside the target region; A-31 confirms which applies. Managed memory (`amrex.the_arena_is_managed=1`) is rejected for production (page-migration cost; it hides data missing on the device) and allowed only as a debugging aid.
- No host-threading OpenMP (`!$omp parallel do` etc.) inside device kernels; OpenMP `target` directives appear only in kernel files. AMReX handles host threading and tiling from the driver. FireX has 0 `!$omp target`/`!$acc` directives, no `cudafor`/`openacc` modules and 356 `!$omp` directives, so the offload variant is written from scratch.
- Two separate sets of bounds: (i) array bounds (fab box plus ghosts, in FDS index space), which only size the dummies; (ii) loop bounds, the only ranges the kernel loops over. On CPU, MFIter tiling makes them differ; on GPU tiling is off and the loop bounds equal the valid box. This is the standard AMReX convention (`lo, hi` plus `BL_TO_FORTRAN_ANYD`).
- Loop ranges come in three kinds, all non-overlapping: the cell tile (`tilebox`); three face tiles (`nodaltilebox(dir)`, one per direction); and a grown tile (`growntilebox(ng)`) for writes into the ghost ring, e.g. `ZZ`. Each tile owns its low faces; only the tile at the box's high edge also gets `hi+1`.
- Fused face nests in `mass.f90` (`DO K=0,KBAR / J=0,JBAR / I=0,IBAR`, e.g. the isothermal FX/FY/FZ correction at mass.f90:328-341 and ADV_FX/FY/FZ at mass.f90:463-468) are split by direction in both P1 variants, on CPU and GPU. On CPU, extending a tile by one at the low end would make tiles overlap, and the in-place correction at mass.f90:331-333 picks its target with `MAXLOC`, so the overlap is a data race. On GPU, the fused nest also evaluates FX on the tangential rows J=0 and K=0, outside the valid face range (wasted work). The Legacy Mapper is adding the list of fused nests to `inventory/kernel_footprint_mass.md`.
- Open parity item (FDS Legacy Mapper, A-34): split nests no longer evaluate FX/FY/FZ on the tangential rows J=0 and K=0. Partial result: nothing in `mass.f90` reads them (users at mass.f90:448, 625 are inside interior loops, 443-445, 620-622), so the core ZZ/RHO comparison (D-022) is unaffected. Still open: (a) `STORE_SPECIES_FLUX` copies those rows into ADV_FX/FY/FZ (mass.f90:463-468, 651-654), read by slice/device output (dump.f90:9850-9898), and whether slice sampling reaches JJ=0 is unconfirmed; (b) CC_IBM `SET_EXIMADVFLX_3D` reads fluxes at `CC_REGFACE_*` indices (ccib.f90:8023-8034), list construction unread. Until A-34 closes, the D-022 frozen-input comparison excludes `STORE_SPECIES_FLUX` and CC_IBM cases.
- Face mask (Legacy Mapper, corrected; scope Chief Architect; extent valid+2 for the D-031 clip; D-031, ADR-001 v0.3.1-v0.3.2): kernels that need wall information at neighbour faces (e.g. the gather clip) take an explicit face-mask argument, separate from `WALL_INDEX`. The mask is nonzero wherever single-mesh FDS would give the face a nonzero `WALL_INDEX`: it is built from single-mesh FDS's `WALL_INDEX` by zeroing only the faces between boxes on the **same level**, never from boundary types. So it covers every domain-boundary face, including OPEN vents and periodic faces (init.f90:76-107), and the clip never redistributes across the domain boundary; on the OBST side it covers exposed faces only (init.f90:199-201 skips domain-facing and permanently covered faces) and marks both sides of a thin obstruction. It stays nonzero at coarse-fine faces, because fine ghosts there are interpolated from the coarse level and a correction taken from them would move mass across levels with no matching coarse change (refluxing does not correct it); this matches FDS treating a mesh interface as a wall. Reason for a separate argument: P1's shim gives every box face an `EXTERNAL_WALL` entry with `WALL_INDEX ≠ 0` (`p1_shim.f90:184-232`), so a gather that read `WALL_INDEX` at box edges would still depend on the layout. Coarse side (Legacy Mapper, accepted by the Architect, ADR-001 v0.3.3): a coarse cell next to a covered cell (one under the finer level) treats that face as a wall in both directions, because average-down overwrites covered cells and any clip mass moved there would vanish; in FDS both sides of a mesh interface have a wall cell (init.f90:76-107). Layout independence therefore covers the box split within a level, not changes in the level structure.
- Domain-wide reductions (D-031; ADR-001 v0.3.1-v0.3.4): a kernel needing one (e.g. the clip flags `CLIP_RHOMIN`/`CLIP_RHOMAX`/`CLIP_RHO_ZZ`) splits into local passes around a host-side `ParallelAllReduce` (AMReX_ParallelReduce.H:236 for `Or`); no cross-box reduction happens inside a kernel. For the clip (D-031 (b)-(e)):
  - Ghosts: second `RHOP` fill OR redundant valid+1 density apply. Target: one pre-clip `FillBoundary` (`RHOS`/`RHO` ng=3, i.e. `RHOP` in the predictor/corrector, mass.f90:789-795; `RHO_ZZ` ng=2) with the density clip, gather and apply run redundantly over the grown tile (valid+1); accepted equivalent: a second 2-layer `RHOP` `FillBoundary` after the density apply (bitwise equal in A-37). Either is needed because the density apply writes `RHOP` in place (853-854) and the species stage uses it as its clip ceiling (887; 907-912 via `RHO_ZZ_MAX`; 934).
  - Native layout: density MultiFab with 3 ghost layers, species MultiFab with 2; the 3-ghost `RHOP` temporary is shim-only.
  - Pass order and the **2-host-sync rule**: density clip and gather (neighbour mass 831-836, scatter 840-846); first OR over `CLIP_RHOMIN`/`CLIP_RHOMAX`; density apply (853-854); all species gathers (independent of each other); second OR over all per-species flags packed into **one** reduction; per-species apply gated by its reduced flag (927); renormalisation (947-961) gated by the reduced density flags OR'd with every reduced species flag (replaces the early return at 943). So each clip call has exactly 2 host synchronisations, whatever the species count.
  - Single species (`N_TRACKED_SPECIES==1`): `RHO_ZZ=RHOP` and return after the density stage (mass.f90:858-860), so one reduction.
  - Two-phase production form (D-031 (f)): per-cell clip terms computed once, then gathered; needs density terms on valid+2 (ADR-001 v0.3.4); the ng=3 input depth still suffices.
  - Conditions (ADR-001 v0.3.2/v0.3.4, stencil verified at mass.f90:775-922): (1) clip flags are set only from valid cells not covered by a finer level, so neither a ghost cell's clip nor a covered coarse cell's clip triggers a renormalisation; (2) `SOLID` (mass.f90:811, 885) and the face mask are defined on valid+2; (3) cell metrics (`DX`/`DY`/`DZ` for `VC`, mass.f90:801-807, 822-828) are defined on valid+3.
  - The clip flags use an exact logical OR, so this does not conflict with the reduction-free race-test scope in acceptance (2).
- Verification: I (P1 code review) + T. Acceptance: (1) the same kernel signature runs CPU-tiled and compiles for the device under CUDA (D-029). (2) Tile-race check (links FR-005 (i)): with a fixed box layout, results are bitwise identical across tile sizes (tiling off included) and OpenMP thread counts 1/2/4/8 with `OMP_DYNAMIC=false`. Scope (Pressure Solver Lead): this applies only to explicit kernels on frozen input that contain no floating-point reductions. It excludes the MLMG solve and its norms, and any kernel that sums across the box outside the FR-005 fixed-point path; those stages keep the within-eps_H rule (FR-005 (iii), D-012) because OpenMP reduction order is unspecified, so a correct pressure solve cannot fail this race test. Phase 1 (P1). Links: R-35, NFR-044, FR-005.
