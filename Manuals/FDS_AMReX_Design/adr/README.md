## Dependency notes
- ADR-002 and ADR-003 assume ADR-001's C++ driver, now owner-confirmed via D-027 (full time step on GPU; F_Interfaces has no GPU support), so ADR-003's EB options stay available.
- **ADR-002 depends on ADR-003:** the solid treatment (pressure spec E-1 IBM vs E-2 masking vs E-3 EB) decides whether the pressure iteration survives for solids; ADR-002 cannot be accepted before ADR-003.
- **ADR-001 depends partially on ADR-003:** choosing EB forces the C++ driver; per-box wall state is the hardest data for ADR-001's `POINT_TO_BOX` shim (R-26).
- Current leanings: ADR-001 Option A (C++ AmrCore driver, owner-confirmed via D-027; Option B rejected definitively), migrated through the `POINT_TO_BOX` shim as a CPU-only stage, then every kernel extracted onto the device (R-26 sets timing only); kernel style K1 (restricted C++ `ParallelFor`) vs K2 (Fortran with `!$omp target teams loop` via nvfortran on an AMReX CUDA build, no-copy `has_device_addr` data, second-compiler portability check; CUDA Fortran only for profiled hot loops with OpenMP fallback) co-equal, decided by the P1 readability review (NFR-044); GPU target NVIDIA only, AMD out of scope (owner, 2026-09-25); second-compiler check optional (`ifx` only); AMR mode uniform grids on each level, stretched cases FDS-only; ADR-002 Option C (single global dt, subcycling-ready data model; matches pressure REC-B1; `FFT::Poisson` on a single uniform level, composite MLMG with `setMaxOrder(2)` otherwise, HYPRE bottom only; Phase 6 scope by D-007); ADR-003 Option B now / D later (OBST staircase per level with the FDS snap rule, D-009; Phase 5 stateful-wall freeze, D-010; pressure E-1 then E-2; EB only with a GEOM decision).
- ADR-002 constrains the pressure-solver design (docs/pressure) and ADR-003 constrains wall-BC mapping (docs/inventory).
