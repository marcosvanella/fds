# tools/ - A-57 enforcement tools for the GPU kernels

These scripts are the enforcement tooling of action A-57 (D-049, D-066; NFR-050, NFR-051, NFR-052). They must exist before the first
new GPU kernel is accepted. They read the generator worktree (branch `s5-gen`, folder `amrex/s4_mass/s5_gen`) and never change it.

Layout convention: the docs repository had no `tools/` folder. The older project scripts (`inventory/*.py`, `sync_design_docs.sh`) live in a
`tools/` folder next to `docs/` that is not under version control, so the A-57 tools are kept here, in `docs/tools/`, where they are
committed with the documents they enforce. The snapshot script `sync_design_docs.sh` copies only `.md` and small `.csv` files, so the
scripts stay out of the public snapshot and are listed in its manifest.

Plain words used below. **K2** = a kernel written in Fortran with OpenMP `target` offload. **K1** = a kernel written as a C++ `amrex::ParallelFor`
lambda. **Callee** = a routine called from inside a kernel loop. **Finding** = one line of tool output. FAIL makes the tool exit 1;
WAIVED means the registry records a reason (printed every time); WARN and NOTE are information.

## Requirements

Python 3.11 or newer (standard library only) and `gfortran` on the PATH (used only as the C preprocessor, to expand the
`!$omp S4_LOOP S4_DEV((A,B))` macros the way the compilers do; set `FC=` to use another one).
The worktree is found with `--tree DIR` or the environment variable `S5_TREE`.

## Run all tests

    python3 -m unittest discover -s tools/tests

Each tool has its own test file in `tools/tests/` with a clean case and mutants (a deliberate violation that the tool must catch).
Tests that need the real generator worktree are skipped when it is absent.

## 1. `k2_ci_check.py` - K2 coding-rule check

    python3 tools/k2_ci_check.py [--tree DIR] [--strict] [--json OUT.json] [-v] [FILE ...]

Scans the K2 Fortran files (`s5_gen/generated/*.F90`, the sidecar kernel goldens `s5_gen/test/*.golden`, the hand-written
`s4_mass_k2*.F90` and `s4d/*k2*.F90`) under six compiler profiles (nvfortran default / callee-bind / bind-all / forced
distribute-parallel-do, gfortran offload, gfortran offload with callee-bind), and every C++ file under `amrex/`.

| Rule | Fails when |
|---|---|
| K2-01 | a directive is outside the approved subset: only `target teams loop`, `target teams distribute parallel do` and a bare `declare target` are approved; host `parallel do`, `atomic`, `critical`, `simd`, `target data`, `taskwait`, OpenACC, `do concurrent` and CUDA Fortran `attributes` fail |
| K2-02 | rule 7 (ADR-001 v0.7): a region that calls a routine, or uses a local array, is not `target teams distribute parallel do` (`target teams loop bind(teams,parallel)` is accepted only under nvfortran) |
| K2-03 | an array dummy used in a region is not in the device-address clause; the clause is `has_device_addr` under nvfortran or `is_device_ptr` under gfortran; an item is not a dummy argument |
| K2-04 | a clause outside the D-029 list: only `collapse(n)`, `private`, `is_device_ptr`/`has_device_addr`, `map(to: ...)` of small host constants, `thread_limit`, `num_teams`, `bind(teams,parallel)` (nvfortran) |
| K2-05 | a kernel body allocates, assigns a pointer, uses `c_f_pointer`, or does I/O or `STOP` |
| K2-06 | a region calls a routine that is not a `declare target` routine in the same set of files |
| K2-07 | the kernel header note is missing (see below) |
| K2-08 | device code in the C++ layer is not in the K1 registry |
| K2-09 | (warning) a registry entry or waiver no longer matches anything |

Kernel header note (K2-07), as the tool defines it: every kernel with a target region has a comment directly above it, or after its
statement, that names the upstream routine and lines (`! func.f90:1348-1354 GET_SCALAR_FACE_VALUE (marker gsfv_central)`); the generator
writes it. A hand-written K2 file (no `GENERATED by s5gen` banner) must in addition say in its header comments what it does about passive
scalars and about the cylindrical terms (ADR-001 S5 answers, NFR-050 (e)); a generated kernel is a faithful translation of the upstream
loop, which keeps both. The `.golden` files hold kernel bodies without their header comment, so K2-07 is checked on the generated file only.

K1 registry: `tools/kernel_registry.toml`. A `[[k1]]` entry (file, function, category, reason, status) allows device code in the C++ layer. The
categories `pack`, `gather`, `scatter`, `checksum` are the data-movement kernels that D-066 allows to be K1 because they contain no physics; any
other category (`reference`, `test-harness`, `physics-fallback`) is always printed as WAIVED. `[[waiver]]` entries accept a K2 finding for now.
`status = "proposed"` means nobody has accepted the reason yet: the tool exits 0 and prints it, `--strict` exits 1.
Exit codes: 0 pass, 1 findings, 2 usage or tool error.
