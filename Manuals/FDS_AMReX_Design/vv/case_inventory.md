## 2. How FDS itself judges pass/fail (measured from the config and scripts)

1. **Dataplot / scatterplot** (`FDS_verification_dataplot_inputs.csv`, 854 rows; driver `FDS_verification_script.py`; logic in `fdsplotlib.py`). Each row pairs "expected" data d1 (an analytical or exact CSV committed under `Verification/<group>/`, or another FDS run) with "predicted" data d2 (FDS output: `_devc`, `_hrr`, `_mass`, `_line`, `_pressit`). A **Metric** reduces each curve to scalars: `end` 548, `max` 88, `area` 61, `mean` 60, `end_1_1` 35, `start` 18, …, `all` (every point), `tolerance` (max |y−initial|), `slope`. The scatterplot step then computes the error, `Relative Error |p−m|/|m|` (612 rows) or `Absolute Error |p−m|` (124 rows), and flags "Out of Tolerance" if it exceeds **Error_Tolerance**. Rows with Quantity `N/A` (105) or `Convergent Series` (4) are plotted only and never fail. Tolerances range from `1e-13` (obst_activation max divergence) and `1e-10` (divergence tests, opening_ulmat) through `1e-3` to `1e-2` (most analytical cases) up to 0.05–0.2 (layer height, flow comparisons). The report is `Manuals/FDS_Verification_Guide/SCRIPT_FIGURES/Scatterplots/verification_scatterplot_output.csv`.
2. **Case-specific Python scripts** print `Python Warning` / `Error` lines. Examples: `saad_mms_temporal_error.py` requires temporal L2 order ≥ 1.99. `shunn_mms.py` requires temporal order ≥ 1.99 for ρ, Z, U and ≥ 0.99 for H, and finest-grid (512) errors e_ρ ≤ 2e-4, e_Z ≤ 1e-4, e_u ≤ 3e-5, e_H ≤ 2e-3. `soborot_mass_transport.py` requires **|L1(4-mesh) − L1(1-mesh)| ≤ 1e-10** plus L1 limits at N=128. The `mass_balance*.py` scripts use balance limits of 1e-5, 1e-6 and 1.5e-3·m. `ns2d.py`, `pulsating.py`, `compression_wave.py` and `vort2d.py` only write error-vs-dx files and plots. Second order is judged by eye in the Guide, so there are no hard gates.
3. **Runtime sanity** (`Verification/README.md`): run in debug mode for a couple of time steps, then `grep forrtl */*err`.

Implication: FDS has **no bitwise or regression-against-previous-version check**, and several convergence studies have no numeric gate. The V&V plan adds both (see `test-plan.md`).

## 3. Runtime estimates: method (ASSUMED, to be replaced by measurement)

`wall ≈ 3 s + cells × steps × C × PI / (ranks × 0.7) + steps × PI × ceil(meshes/ranks) × 50 µs`
- `steps = T_END·U/(CFL·dx_min)`, where U is an assumed peak speed per case. It is replaced by T_END/DT for fixed-DT inputs and by explicit values for VN-limited DNS cases.
- C is the single-core cost per cell-step: iso-2D 1 µs, iso-3D or DNS 2 µs, fire 5 µs, fire+radiation 8 µs, solid 3 µs.
- PI is the pressure-iteration multiplier: 1.5–3 for tight VELOCITY_TOLERANCE; **10** for the `ns2d_16_*_refinement` cases (VELOCITY_TOLERANCE 1e-6, up to 100 iterations); 7 for the 1 M-cell UGLMAT/HYPRE GPU inputs (AMG-PCG to 1e-12, twice per step).
- The last term (new in v0.2) is a per-mesh exchange overhead. It dominates only for tiny many-mesh cases such as the 13-mesh `ns2d_16_int_1to2_refinement` on 1 rank.
- Memory ≈ 1.2 GB per million cells *(assumed rule of thumb)*. Every Tier 1/2 case is below 0.4 GB except the optional 1 M-cell `VV/test_8mesh_NOFRPG_short` (~1.2 GB). The real constraint is the 2–6 GB of RAM that other workloads currently leave free.

**Treat every runtime as ±3×.** Reference capture will record measured wall times (`.out` "Total Elapsed Wall Clock Time", `_cpu.csv`) and re-tier.

Category key: (a) multi-mesh / interface / mixed resolution, (b) pressure / Poisson / MMS, (c) conservation, (d) scalar transport, (e) grid- or time-convergence series, (f) fire/plume end-to-end, (g) restart / determinism, (h) particles, (i) radiation, (j) timing/performance, (k) output format.

**Why three are commented out.** `git blame -L 3,6 Verification/FDS_Cases.sh` puts all three commented lines in commit `042aa2624d` (R. McDermott, 2024-11-08). The subject line is: *"FDS Verification: updates to amr test cases, demonstrating errors in both embedded mesh strategy and interpolated refinement."* That same commit created `ns2d_16_int_1to2_refinement.fds`, switched the two `emb` cases to `&VENT DB=... PERIODIC`, and removed `FLUSH_FILE_BUFFERS`. So the cases were added **commented out on purpose, as demonstrations of known error** in FDS's two existing ways of coupling meshes of different resolution. They were not disabled for crashing or for runtime. None has a dataplot row, a committed expected-result file, or a Verification Guide section. The last activity on these lines is that 2024 commit (checked through FireX HEAD). There are no comments in the input files.

**Implication for A-09.** "Passes on baseline" has no FDS definition for these cases. V&V proposes: (i) the case runs to T_END=30 s without NaN or instability, on GNU and on Intel; (ii) the RMS and probe (UVEL, PRES at the domain centre) errors against the analytic solution are recorded (computed the way `ns2d.py` does for `ns2d_16`); (iii) these errors become the baseline values for later T2 "no worse than baseline" comparisons. We **expect** baseline refined-patch errors to be *no better* than the uniform-coarse `ns2d_16` error. That is the documented defect, so FR-014's "refined ≤ coarse" can't be demonstrated on baseline; it is a target for the AMR code. Size: 320–512 cells, 2-D. T_END=30 s is about 4.8× the `ns2d_16` horizon (2π). Step count is about 1.8 k at CFL 0.25 with dx=π/16 (~0.9 k for the 1:1 case).

**GPU_Tests on the CPU-only development machine.** No GPU is present. Everything in the folder is CPU-runnable **as physics**: with a CPU build, `HYPRE_DEVICE_RUN` (default `.TRUE.`, cons.f90:569) is compiled out (`#ifdef WITH_HYPRE_DEVICE`), When `FDS_RANKS_PER_GPU` is unset, FDS prints a note and uses 1. That variable is **not** GPU-only, though: with N>1, ranks are grouped into "resource sets" and only each set's master gathers and solves the global matrix (`MPI_GATHERV` on `MPI_COMM_RS`, pres.f90:3411-3440, 4479-4573). So it changes HYPRE's row partition on CPU as well (this is FR-038's resource-set logic). The `*_runjob.sh`, `submit_all.sh` and `set_affinity_gpu_polaris.sh` scripts target Aurora (ALCF), Frontier (ORNL), Polaris (ALCF) and Vista (TACC) batch systems and **do not apply here**. The `_RS*` vs `_NOFRPG` inputs differ only in CHID. Their job scripts differ only in `FDS_RANKS_PER_GPU` (e.g. 4 vs 1). Run with the same value, they are a free T0 determinism pair. Run with their intended values, they are a CPU check of the FR-038 resource-set path: T1 against baseline at the same setting, round-off-level (T2) against each other. The 16- and 32-mesh variants need 16/32 ranks (no MPI_PROCESS), so on 8 cores they would need oversubscription or a V&V copy with MPI_PROCESS. Full runs cost 20–45 min each at 8 ranks *(est.)*, which is why only one shortened copy is scheduled (`VV/test_8mesh_NOFRPG_short`, T2-opt).

**AMR / HYPRE relevance.** High for the pressure work. These inputs are the only ≥ 1 M-cell, multi-mesh UGLMAT/HYPRE cases in the suite. Settings: PCG + BoomerAMG, `HYPRE_SOLVER_TOL = 1e-12`, max 1000 iterations (imkl.f90:238-263), `MAX_PRESSURE_ITERATIONS=1`. That makes them the natural baseline for (a) HYPRE cost and scaling on the development machine (NFR-030, NFR-033 candidate), (b) the solver-tolerance number FR-016(c) and FR-031 need, and (c) the 4/8/16/32-mesh decomposition sweep at fixed global size, the same comparison as "one AMReX level, many boxes" (FR-002, IR-004). The fire makes them chaotic: T1 holds only over the first steps, so use them for cost and residual checks, not long-horizon regression. `test_gpu.fds` is the same case as `test_8mesh_*` but with `SOLVER='UGLMAT HYPRE'`, default pressure iterations and T_END=1 s.

**VTK on the development machine.** All 4 inputs are CPU cases, but `WRITE_FORMAT='VTK'` writes **VTKHDF** files. Those need a `WITH_HDF5` build: the makefile builds HDF5 1.14.5 through `build_thirdparty_libs.sh` only if `$FIREMODELS/hdf5` (a clone at tag `hdf5_1.14.5`) exists, and the CMake build has no HDF5 option at all. VTK mode also sets `WRITE_SMV=.FALSE.` (read.f90:2429-2441), so no `.smv` is written. CSV output is unaffected. There is no pass/fail criterion (not in `FDS_Cases.sh`, no dataplot row), so these are Demonstration-only (D). `couch.fds` is long (600 s fire, est. ~35 min); `cascade.fds` (1 mesh, 14 k cells, ~2 min) is the cheapest output-format probe. **AMR relevance:** not for the solver, but directly relevant to FR-072/FR-073 and Q5. VTKHDF has an overlapping-AMR dataset type, so this writer is a candidate route for refined-level output that avoids re-listing boxes as Smokeview `GRID` blocks every regrid. Recommendation: no gate now; add a D-type check with `cascade.fds` once the FireX build includes HDF5, and involve the Chief Architect when Q5 is decided.
