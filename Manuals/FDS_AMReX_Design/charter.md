# FDS-AMR project charter

Owner: Spec & Program Lead · Status: draft v0.4.21 (2026-09-26; changelog in README.md) · Source pin: FireX 36975d765f on branch `FDS-AMReX` (this repository; renamed from `AMReX`, D-037)

## 1. Problem statement

FDS resolves a fire scenario on a fixed set of user-defined rectilinear meshes. Resolution can vary only where the user places meshes of different cell size, and those meshes never change during a run. What the code does today (all references checked at FireX `36975d765f`):

- **Static multi-mesh.** Each mesh is one `MESH_TYPE` element of the global array `MESHES` (mesh.f90:16-356). Kernels reach mesh data through module-level pointers reassigned by `POINT_TO_MESH(NM)` (mesh.f90:505-916), which is called from 214 sites in 19 source files (FireX's new `vtkf.f90` is one of them). Meshes are assigned to MPI ranks at input (`MPI_PROCESS` on `&MESH`, read.f90:614-711), and there must be at least as many meshes as ranks (read.f90:571).
- **Coupling only at mesh exteriors.** Neighbour data is copied into per-neighbour `OMESH` buffers (type.f90:1033-1078) by `MESH_EXCHANGE(CODE)` (main.f90:3117) and applied through `EXTERNAL_WALL` cells of type `INTERPOLATED_BOUNDARY` (e.g. `ASSIGN_GHOST_VALUE`, wall.f90:282; `MATCH_VELOCITY`, velo.f90:2618).
- **Coarse/fine abutment exists but is limited.** Meshes of different resolution may touch if the fine faces tile each coarse face exactly (alignment check, init.f90:3184-3226, ERROR(431)). Ghost values are area-averaged (wall.f90:315-347) and normal velocities are area-matched (velo.f90:2618-2857). An embedded fine mesh receives data from the coarse mesh but sends nothing back: the User Guide says the coarse mesh "is not affected by the smaller, usually finer, mesh embedded within it" (FDS_User_Guide.tex:1112).
- **Per-mesh FFT pressure solve.** The default solver is a Fishpak FFT solve per mesh (`PRESSURE_SOLVER_FFT`, pres.f90:318). It requires a tensor-product grid that is stretched in at most two directions (init.f90:2356-2366, ERROR(425)). Meshes are coupled by Dirichlet values of H at interfaces (pres.f90:16-315), and an iteration (`PRESSURE_ITERATION_SCHEME`, main.f90:1601-1745) reduces the normal-velocity mismatch at solid and interpolated boundaries. Global sparse alternatives (GLMAT/UGLMAT through the MKL cluster solver or HYPRE, pres.f90:3299-3902; ULMAT per mesh, pres.f90:1131, 1423) exist. UGLMAT is the only one documented to handle refinement, and only for non-overlapping meshes (FDS_User_Guide.tex:9455).
- **FireX: HYPRE pressure solve can be offloaded to GPUs.** FireX adds no new `SOLVER` options (`DEFINE_PRES_METHOD`, func.f90:7143) and leaves the FFT path unchanged (`PRESSURE_SOLVER_FFT`, pres.f90:318). It adds a GPU build of HYPRE (CMake `USE_HYPRE_NVIDIA`/`_AMDGPU`/`_INTELGPU`, CMakeLists.txt:16-18; defines `WITH_HYPRE_DEVICE`) and `&PRES HYPRE_DEVICE_RUN` (default `.TRUE.`, cons.f90:569), which sets the HYPRE memory location and execution policy to the device (e.g. pres.f90:1178-1184, 4432-4438). It also adds "resource sets": the `FDS_RANKS_PER_GPU` environment variable groups ranks per GPU (`DEFINE_RS_COMM_INFO`, main.f90:5096). For GLMAT/UGLMAT, matrix and vector data are gathered to one master rank per set, which alone calls the solver (pres.f90:3411-3421). The PCG tolerance is a fixed parameter (`HYPRE_SOLVER_TOL = 1.D-12`, imkl.f90:239). This is library offload of the linear solve only; no FDS kernel runs on a GPU.
- **FireX: second output path.** `vtkf.f90` writes VTKHDF files (`UnstructuredGrid` for gas, slices and boundaries; `PolyData` for particles; vtkf.f90:678, 758) with parallel HDF5, plus a ParaView state file. It is selected by `&DUMP WRITE_FORMAT` (`'SMV'` default, `'VTK'`, `'BOTH'`; read.f90:2382, 2429-2440). It needs HDF5 (`WITH_HDF5`), which only `Build/makefile` wires up; `CMakeLists.txt` has no HDF5 logic (unconfirmed by a build, A-14). Smokeview output is unchanged apart from an optional `SMOKE3D_VERSION=2` 3-D smoke format.
- **One global time step** for all meshes (`DT = MINVAL(DT_NEW)`, main.f90:715, 891). FireX does not change the time loop, mesh decomposition or pressure iteration beyond renames and additions: `MASS_FINITE_DIFFERENCES_NEW` → `MASS_FINITE_DIFFERENCES`, a wall-clock stop (`T_END_CLOCK`, main.f90:1199), and VTK/HDF5 calls.

The consequence: a user who wants fine cells near a fire, a sprinkler spray, or a leakage path has to guess, before the run, where those regions will be. Mismatches at the interfaces are controlled only by an iterative tolerance. Refinement that follows the fire as it spreads is impossible.

## 2. Goal

Give FDS block-structured AMR through AMReX: a hierarchy of properly nested uniform Cartesian levels, refined and coarsened during the run according to solution criteria. FDS physics and its verification record stay intact.

## 4. Scope

**In scope:** gas-phase transport on an AMReX hierarchy (Cartesian 3-D; 2-D Cartesian TBD); static and dynamic refinement; conservative coarse-fine coupling; composite pressure solve; rectilinear OBST/VENT on refined levels, including thin obstructions; HVAC, pressure ZONEs and level-set wildfire with refinement (owner decision on Q4, D-033); Lagrangian particles; radiation coupling; DEVC/HRR/mass outputs; Smokeview-format output including refined levels, plus FireX VTK output, in AMR runs (owner decision on Q5; FR-072, FR-074); running the FDS Verification inputs that cover in-scope features (FR-006); restart; MPI + OpenMP on CPU; GPU execution of the full time step on NVIDIA GPUs (CUDA backend; D-027, NFR-043); CMake build.

**Scope change (D-027, 2026-09-25).** Running the full time step on the GPU substantially widens scope: every physics kernel must be ported to the device, not only the driver and pressure solve. The schedule impact is TBD until ADR-001 S4 (GPU cost probe) gives a porting estimate.

**Non-goals.** Items marked ASSUMPTION need confirmation by the project owner (Q-list in §9).
- No changes to physics models (combustion, turbulence, pyrolysis, radiation model, droplet physics). ASSUMPTION (D-003).
- No rewrite of FDS physics kernels in C++ is assumed. Under D-027 the kernel style (restricted C++ `ParallelFor`, or Fortran with simple OpenMP `target` offload through `nvfortran` per the owner decision in ADR-001 v0.3; OpenACC rejected; CUDA Fortran only for profiled hot loops with OpenMP fallbacks) is chosen after the P1 readability review by FDS Fortran developers (NFR-044). The C++ AMReX driver is decided (D-027). Particles (R-28) and, if ADR-003 picks EB, the pressure path push toward C++ at the driver level, not in the kernels.
- Deferred, not permanently dropped: complex geometry (`&GEOM`, CC_IBM: ccib.f90 24,046 lines + geom.f90 27,735 lines) and HT3D with refinement (owner decision, 2026-09-25; D-033). Consistent with the existing CC_IBM exclusions (`cascadempi` under D-022/A-34; `Complex_Geometry/*` excluded from the V&V inventory; FR-044). With refinement they stop at setup (FR-004).
- No AMD (HIP) or Intel (SYCL) GPU support. NVIDIA is the only GPU target; AMD is out of scope, not deferred (owner decision, 2026-09-25, relayed by the Chief Architect; D-027). A second OpenMP-offload compiler (ifx) is optional and non-gating (NFR-045).
- No stretched grids (`TRNX/TRNY/TRNZ`) in AMR mode. AMR mode uses only uniform grids on each level; stretched cases stay FDS-only (decided: owner decision, 2026-09-25, relayed by the Chief Architect; D-030, IR-002).
- No AMR support for `CYLINDRICAL` meshes; they are rejected in AMR mode. ASSUMPTION, awaiting the project owner under Q4 (11 Verification inputs affected; FR-006).
- No subcycling in time in the first multi-level phase (ADR-002 leaning; still open).
- No changes to the Smokeview source.
- No upstream contribution process to FireX or firemodels/fds is assumed for now: the code lives in the project owner's fork, and going upstream (FireX or `firemodels/fds` master) is decided later (Q3, decided for now, upstream open-later; owner decision, 2026-09-25). The upstream path is kept possible by the guiding constraint in §7. Rebase policy: D-034 (Q10 answered).

## 6. Success metrics

1. In uniform mode, explicit kernels (mass, velocity predictor, divergence) on frozen input match single-mesh baseline FDS within T1, T0 per Q1 (requirements §2.2); multi-mesh anchors are checked through equivalent single-mesh inputs. Whole anchor runs match baseline within T2: after the first pressure solve bit-parity is infeasible, because Crayfishpak is replaced (D-021, D-022). Target: 100% of the anchor list.
2. The FDS verification cases in the supported feature set that pass on baseline also pass in uniform mode. Target: 100%, with each exception documented and approved.
3. On multi-level conservation tests, the relative mass and species imbalance per run stays at or below the FR-020 target (proposed: 1e-12 relative per step, 1e-10 cumulative).
4. Composite pressure solve: normal-velocity mismatch at coarse-fine faces at or below the solver tolerance (FR-032).
5. Plume benefit case: error vs uniform-fine within the T3 tolerance at ≤ 50% of uniform-fine wall-clock time (proposed, NFR-032).
6. Uniform-mode runtime ≤ 1.25× baseline on the development machine (proposed, NFR-030).

## 7. Constraints

- Development and test machine: 8 CPU cores, 16 GB RAM, no GPU; gfortran 14.2 + OpenMPI 5.0.7 (reinstalled 2026-09-25 after a Sep 23 reset wiped apt packages). Intel oneAPI restored 2026-09-25 under `/opt/intel/oneapi` (ifx/icx 2026.1.1, Intel MPI 2021.18.1, MKL 2026.1; A-18 closed; R-32). No GPU, so GPU work on this machine is compile-only plus host fallback (R-38; NFR-043). Scaling evidence is limited to 8 ranks. Large validation cases are out of reach unless more compute is provided (Q6). GPU test hardware (Q11 (b)): an owner-provided NVIDIA test machine is coming online (a single GPU; model not recorded; no date yet). Multi-GPU and multi-node testing for NFR-047 needs other hardware; no cluster is named and budget and date are open (Q6, R-45).
- Dependencies must come from public sources or local mirrors.
- The reference tree (this repository; FireX `36975d765f`, branch `FDS-AMReX`, also on the project owner's fork as `marcosvanella/fds:FDS-AMReX`; D-037) is read-only until after the spec phase: no edits, commits or further branch operations (D-005; amended by D-044: the only commits allowed during the spec phase are documentation snapshots under `Manuals/FDS_AMReX_Design/`, generated by `tools/sync_design_docs.sh` and approved by the AMR Chief Architect). Builds go out of tree. `(local FDS master checkout)` (`ce1f659`) is a read-only comparison copy. All work goes under `(local project directory)`. After the spec phase the AMR Chief Architect approves and makes the first commit to `FDS-AMReX` (commits authored under a dedicated project identity; pushes only with the project owner's approval; D-037); once development starts, FireX is merged into `FDS-AMReX` daily, replacing the frozen `36975d765f` pin for development (D-034). V&V baselines and source line citations are then re-pinned at each milestone, every daily merge gets a quick Tier-1 smoke run, and spec citations name the milestone pin they refer to (adopted plan pending V&V Lead confirmation, A-42; R-44).
- **Guiding constraint: keep an upstream path possible** (Q3, owner decision). The code lives in the project owner's fork for now; whether it goes upstream to FireX or `firemodels/fds` master is decided later. Keep NIST FDS conventions wherever they are cheap to keep, so the upstream path stays open. Only conventions that can be cited from the FDS documents or source are written down as requirements (NFR-041); where keeping one is expensive, the trade-off is recorded in an ADR or the decision log rather than silently dropped.

Whether S-A is kept as an optional exact mode is for the AMR Radiation Lead to propose later; it is not a requirement. *Original question:* Should the radiation sweep across the boxes of one level be **S-A**, an exact dependency-ordered sweep across boxes (the radiation stage is independent of box split, rank count and thread count, so byte-identical across box splits under FR-005 (i); radiation is outside the D-022 bit-parity scope against FDS), or **S-B**, FDS-style lagged exchange of box-face intensities once per angle cycle (depends on the box split; needs an explicit FR-005 (i) exemption)? The AMR Radiation Lead recommends S-A as default with S-B as a performance option (`radiation/01-radiation-amr-spec.md` §2, §7 Q1, draft). | FR-061 (radiation in uniform mode, Phase 2) depends on it, and its FR-005 status must be recorded before M2. S-A may not scale on GPUs or many ranks (R-51); S-B's lag grows as boxes shrink (R-52). A choice of S-B needs your approval of the FR-005 exemption. |
