# FDS-AMR roadmap

Owner: Spec & Program Lead · Status: draft v0.4.39 (2026-10-04; changelog in README.md) · Source pin: FireX 36975d765f on branch `FDS-AMReX` (this repository; renamed from `AMReX`, D-037)

No calendar dates are set. Durations are **estimates** in elapsed working weeks for the current team on the current box. Confidence is low until Phase 1 closes; they are re-estimated at every milestone. Requirement IDs refer to requirements.md; risk IDs to risks.md.

## Principles

1. Every phase ends with a measurable gate tied to requirement IDs. Any gate that uses a proposed number needs the project owner's approval of that number first.
2. Keep FDS runnable at every step. With `USE_AMREX=OFF` the build must equal baseline (IR-006).
3. Add numerics before subsystems: uniform first, then multi-level transport, then pressure, then walls, then everything else.
4. Machine limit: 8 cores, 16 GB, no GPU. Any test that does not fit is deferred and logged, not dropped silently. GPU execution of the full step is required (D-027, NFR-043), but on the development machine GPU work is compile-only plus host fallback (R-38). FireX's HYPRE GPU offload must stay compilable and is checked on CPU only (FR-038, R-40).
5. Code base: FireX `36975d765f`, branch `FDS-AMReX` (D-005, D-037), kept on the project fork (Q3, decided for now; going upstream is decided later, and NIST conventions are kept where cheap, charter §7). The branch is read-only through Phases 0-1. No code lands on it before M1 (amended by D-044: during the spec phase the only commits allowed are Chief-Architect-approved documentation snapshots under `Manuals/FDS_AMReX_Design/`, generated by `tools/sync_design_docs.sh`); after the spec phase the AMR Chief Architect approves and makes the first commit (D-034; commits authored under a dedicated project identity, pushes only with the project owner's approval, D-037). From then on FireX is merged into `FDS-AMReX` daily, each merge gets a quick Tier-1 smoke run, and V&V baselines and source line citations are re-pinned at each milestone (D-034; adopted plan pending V&V Lead confirmation, A-42; R-44). Spikes before then build from copies outside the worktree.
6. Environment check at every milestone entry. Run the scripted toolchain check (A-21): GNU 14.2 + OpenMPI 5.0.7, oneAPI, HYPRE (FireX-fetched `63331f19c7` = v2.32.0-24 and the development machine's 3.0.0, versions from build provenance), FFTW headers. Record the versions next to the baselines. A missing toolchain blocks only the gates that need it, and is logged (R-32).

Conservation check: if FR-014/022/023 fail or pass only marginally, the cause is fixed within Phase 4. No sync projection is needed under a global dt, so this is not an R-05 trigger; R-05's gate is now the Phase 6 sync-correction decision (subcycling is ruled out, D-050) (Pressure Lead, 2026-09-25). **R-26 shim-exit review** if ADR-001 adopts the shim: a kernel-extraction date is set, and the regrid rebuild measured in P3/Phase 3 is ≤ 10% of step time.
